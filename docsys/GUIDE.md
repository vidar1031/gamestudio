# docsys 采纳指南——为你的项目建立 GB/T 8567 文档体系

> 读者：任何项目工程的负责人/开发者。本文不出现任何具体产品名；文中 `<产品册>` 指你的产品名占位（小写英文目录名），「你的产品」指要接入的项目。
> 本文随 docsys/ 目录一起走：拿到目录即拿到本指南。

## 1. 这是什么

docsys 是一套**把项目全部知识表达出来**的文档体系与零依赖静态站点框架：

- **框架**（`framework/`）：Markdown 渲染器、构建器、本地预览、图形引擎（流程图/组织图/分层图）、GB/T 8567 十四件国标骨架模板。不含任何项目内容，可整体拷走复用。
- **数据**（`content/`）：你的产品册——一组 Markdown 文档实例 + 一个 `manifest.json` 册目录。

你只需写 Markdown，构建即得一个深色主题、可检索目录、带进度统计与图形的文档站。

## 2. 它能解决什么

1. **用户学习**：用户手册按"你要做什么"组织，逐步操作 + 真实案例，用户照着就能用你的产品。
2. **新人/新 agent 接手**：规则、定义、设计概念都有落档位置，不靠口口相传。
3. **评审与治理**：每篇文档有状态流转（未开始→编写中→评审中→完成），首页自动统计进度。
4. **定义先行**：先把"系统必须满足什么"写清楚再实施，实现与定义不漂移。

## 3. 采纳步骤（十分钟跑通）

```bash
# 1. 把 docsys/ 目录拷进你的仓根
# 2. 删掉 content/ 下别人的册，建自己的册：
mkdir -p docsys/content/<产品册>
# 3. 照示例写 manifest.json（声明分组与文档清单，见 §4）
# 4. 在你的 package.json 加三个脚本：
#    "docsys:scaffold": "node docsys/framework/scaffold.mjs"   # 如框架带脚手架
#    "docsys:build":    "node docsys/framework/render.mjs"
#    "docsys:serve":    "node docsys/framework/serve.mjs"
# 5. 生成骨架 → 填充内容 → 构建 → 预览
npm run docsys:scaffold && npm run docsys:build && npm run docsys:serve   # 默认 8891 端口
```

构建产物在 `docsys/dist/`（纯静态）。**建议把它挂到你的业务后端静态路径**（如 `/docs/`），产品里放一个「帮助」入口直达——用户不必另起预览服务。

## 5. 表达方法论（核心规则）

### 5.1 定义先行，全局超前
先写"系统必须满足什么"（定义级），再实施；某项能力未落地不影响定义成立。**定义是目标产品的完整描述，不是当前进度说明**。定义与现状的差距只允许出现在"实现映射"注记里（一行登记：已实现到哪、谁先行）。

### 5.2 层级纪律（防淹没）
- 统筹层文档（01–07、PRD）只写"系统必须满足什么"，**不出现具体案例名与任务代号**。
- 案例与任务过程只进 08/09/10/13/14（手册与过程记录）。

### 5.3 文案三寄存器
| 寄存器 | 出现在哪 |
|---|---|
| 用户语言 | 界面默认、手册正文——读者看得懂的动作与结果 |
| 技术语言 | 折叠区、设计文档、诊断区——成行成组有标题 |
| 测试/调试文字 | **禁止出现在任何正式界面与统筹层文档** |

### 5.4 界面定义的统一写法（上帝视角，五件套）
每个界面一篇，固定骨架：
1. **定位**：这个界面回答用户的哪几个问题（+非目标）
2. **页面结构**：组织图（`chart org`）
3. **区域/功能逐项定义**：每个元素"是什么/行为是什么/可见条件"
4. **状态与流转**：逻辑图（`chart flow`，含失败与取消路径）
5. **数据流 + 代码结构**：分层图（`chart layers`）+ **真相文件树**（代码围栏内缩进路径 + `#` 注释，真相以仓内文件为准）
6. 收尾：自适应行为、文案与令牌应用

### 5.5 图形纪律
- `chart flow` = 逻辑流转（状态机/流程/判定）；判定节点标签以"？"结尾成菱形
- `chart org` = 组织/页面结构（从左向右生长）
- `chart layers` = 逻辑分层（数据流/架构层）
- **代码结构一律不用图**——用真相文件树（见 5.4-5）

### 5.6 单一真相源与台账
- 内容可引用仓内既有文档（manifest 的 file 支持相对路径），不复制。
- 数值台账（行数/性能/进度）写在文档里就必须随波次滚动更新；记假账比不记更坏。

### 5.7 状态流转
每篇文档 front-matter 写 `status: 未开始 / 编写中 / 评审中 / 完成`，首页进度据此自动统计。建议每月一次 30 分钟评审会，批量推进"编写中→评审中→完成"。

## 6. 让用户学会你的产品：手册写法

08 用户手册是用户学习的正门，强制要求：
1. **按"你要做什么"组织**，不按界面罗列功能。
2. 全流程逐步说明：每一步写清"点哪里、等什么、出问题怎么办"。
3. **至少一个完整案例**：选一个真实任务，从第一步走到产物交付，逐步给预期耗时与卡点处置。
4. 术语表用"人话"（先给比喻，再给定义）。
5. FAQ 只收真实踩过的坑。

## 7. 建成验收口径

一个项目的文档体系算"建成"，当且仅当：
1. 十四件国标 + 你的扩展组全部起稿，状态无一长期停在"未开始"。
2. 每个面向用户的界面都有界面定义（五件套齐全）。
3. 一个新用户只读《用户手册》就能独立走通主流程（实测，不是印象）。
4. 站点挂进产品的帮助入口，用户一键可达。
5. 月报在位且连续（证明它是活文档，不是一次性工程）。

## 8. 常见问题

- **Q：框架升级了怎么办？** 目录拷贝模式下各仓自维护；多项目长期使用建议把 `framework/` 抽成独立包/模板仓，一处升级多处受益。
- **Q：文档会不会写完就死？** 用状态流转 + 月报节奏驱动；把"改代码必须同步文档"写进你的工程纪律（如改动涉及文档描述的模块，同提交更新）。
- **Q：内容文件能引用仓内代码/文档吗？** 能，manifest 的 file 支持相对路径（如 `../../../docs/xx.md`），保持单一真相源。
