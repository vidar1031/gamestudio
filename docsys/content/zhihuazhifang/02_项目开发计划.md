# 项目开发计划

> 本计划站在全程序视角编制：管"做什么、谁来做、按什么顺序、按什么标准验收、关键风险是什么"。
> 写作纪律（全局统筹层）：不写进度日志、不记具体案例名与任务代号；案例与执行过程属月报/总结报告范围。
> 输入源：《产品说明书》、《可行性研究报告》、《软件需求说明书》、《总监自治实施方案》、《工程升级实施方案》、《故事生产能力矩阵》。

## 1. 引言

### 1.1 编写目的
规定织话智坊（互动故事生产工具）开发、测试、文档、发行全过程的任务分解、人员组织、进度门禁与资源配置，作为项目执行与检查的依据。

### 1.2 背景
- 项目名称：织话智坊（互动故事生产工具）。
- 委托/开发/使用单位：同一团队（本地研发，后期发行）。
- 系统格局：守护台（控制平面：编排/审核/调度/治理）+ 业务面（编辑器+业务后端）+ 文档体系（docsys）+ 真相源存储。

### 1.3 定义
WBS：工作任务分解。验证门：阶段放行必须全部通过的硬性检查项。适应度函数：一条命令可复跑的全部护栏集合。

### 1.4 参考资料
《产品说明书》功能总规格与路线图、《可行性研究报告》、《总监自治实施方案》（自治线验证门）、《工程升级实施方案》（工程线阶段）、《运行时能力测试基准》（硬件硬约束）。

## 2. 项目概述

### 2.1 工作内容
本项目工作内容覆盖六个范围域：
1. 产品功能建设与完善（需求说明书 F1–F9：故事结构/视觉资产/场景合成/审图闭环/运行交付/治理/文档体系/可打包性）；
2. 工程外壳升级（编辑器外壳、服务端与控制面分层模块化）；
3. 生产自治能力演进（看门狗/资源自愈/策略表数据化/工作流声明化）；
4. 文档体系建设（GB/T 8567 全套 + 产品扩展文档）；
5. 测试与质量保障（四阶段基准、黄金基线、发行验收）；
6. 运营筹备（推广基础设施、机构渠道、发行商务模式）。

### 2.3 产品

#### 2.3.1 程序（最终移交）
- 桌面应用包（业务面+控制面双服务、模型与依赖安装器）；
- 自托管站点包（服务端形态）；
- 文档体系站点（docsys 静态产物，随发行附带）。

#### 2.3.2 文件（最终移交）
GB/T 8567 全套（本册 14 件）+ 产品说明书 + 市场与竞品分析 + 用户/操作手册 + 发行说明模板；全部入 docsys 册管理。

#### 2.3.3 服务
安装培训、首年维护、机构定制服务（收益模型见可行性报告 §6.5）。

#### 2.3.4 非移交产品
生产过程资产（各测试故事的真相源目录）、内部评审记录、运行日志、开发中间件。

### 2.4 验收标准
- 总体验收口：发行验收 = 连续 3 个故事零人工干预生产 + 走查评分 90+ + conformance 套件全绿 + 文档体系 14 件全部"完成"态。
- 每里程碑有独立验证门（见 3.3），不过门不进下一阶段。
- 需求逐项可追溯：SRS 编号 → 概要设计模块 → 测试用例，三链一致。

### 2.5 完成项目的最迟期限
不设硬死线，设里程碑评审节奏：每月一次月报（13 号文档）+ 每里程碑门口径评审。建议目标窗：M2（视频形态）3 个月内，M4（打包 β）6–9 个月内。

### 2.6 本计划的批准者和批准日期
产品负责人；批准即转 v1.0 实施态。

- 需求与验收接口：规则统筹师（需求基线变更必须经其登记评审）。

### 3.3 进度（里程碑与验证门）


| M2 视频形态 | 预演视频导出+自动演示机制 | 三平台预设样片各一条；演示模式无人值守全片播放 | T+3 月 |

### 3.4 预算
- 现金支出近零（存量硬件+开源/自研软件）；主体投入为人力工时。
- 单项外购上限纪律：任何新增付费依赖（素材/字体/服务）必须过评审并登记。

### 3.5 关键问题
| 关键问题 | 影响 | 对策 |
|---|---|---|
| 32G 资源墙反复撞 | 生产中断 | 自治线资源自愈优先实证；人工处置模式已固化过渡 |
| 本地模型内容天花板 | 画面表达受限 | 工艺件+确定性合成兜底；提示词配方纪律 |
| 市场窗口演进快 | 推广位被同质内容占据 | 视频形态（M2）前置；差异化不打正面战场 |
| 文档滞后于代码 | 接手成本飙升 | WP-F 与开发同步滚动；文档完成度进里程碑门 |
| 单人+agent 模式单点 | 负责人不可用时停摆 | 文档体系+台账即继任者指南；关键决策全部落 ADR |

## 4. 支持条件

### 4.1 计算机系统支持
开发/生产同机：32G Apple Silicon Mac；本地模型服务、出图服务、视频合成工具、浏览器；固定端口分配见 SRS §4.3。仓库双仓格局（业务仓+控制仓）+ 文档体系目录。

### 4.2 需由用户承担的工作
- 试运行用户：提供真实题材需求、验收样片与交互包、反馈缺陷。
- 机构试点用户（M4 后）：提供部署环境与合规要求清单。

### 4.3 由外单位提供的条件
无硬性外部依赖（本地优先设计原则）；可选云端评审/配音服务均须有本地兜底路径。

## 5. 专题计划要点

### 5.1 配置管理计划
- 真相源即配置项：项目目录/计划/状态/评审记录；双仓 git 管理代码与文档。
- 变更控制：契约（schema/API/事件名）变更必须双仓同步+测试；文档状态流转（未开始→编写中→评审中→完成）在 docsys 登记。

### 5.2 质量保证计划
- 适应度函数一条命令全跑（静态/单元/生产基准/黄金基线），每波迭代必过。
- 评审纪律：代码评审走提交记录；文档评审走 docsys 状态流转；内容评审走审图门禁。
- 缺陷登记制度：发现即登缺陷录，修复后归档，月报汇总趋势。

### 5.3 测试计划要点
四阶段基准为骨架；每里程碑补当期的测试分析报告（12 号文档）；黄金基线随功能演进更新基线值（更新需评审）。

### 5.4 文档计划要点
docsys 为唯一文档生产与发布通道；十四件按依赖序推进（SRS→概要设计→数据→详细设计滚动→测试→手册→过程记录随写）；每里程碑门口径检查文档完成度。

### 5.5 风险管理计划
关键问题表（§3.5）逐月复审；风险等级变化进月报；新增风险即登记。

### 5.6 培训与交接计划
新成员路径：治理宪法三篇 → 能力矩阵与缺陷录 → 一条生产链纵切代码 → 控制面两模块；交接以文档体系+台账为准，口头传承不算交接。
