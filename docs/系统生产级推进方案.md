# 系统生产级推进方案

本文是 `docs/` 中唯一用于推进 GameStudio 达到生产级的方案文档。它只保留当前有效的目标、边界、任务流、已具备能力摘要和未实现项；历史实施日志、单次测试结果、旧阶段复盘和重复说明不再写入本文。

## 生产级目标

GameStudio 的生产级目标是：用户给出互动故事 brief 后，Control 能驱动 Hermes/OMLX 与 GameStudio Server，生成可验证、可编辑、可导出的 H5 互动故事项目。

系统判断标准不是“模型能回答”，而是完整任务链是否能留下可追溯证据：计划、审核、执行结果、项目文件、校验结果、导出产物和失败边界。

## 系统分工

| 层 | 职责 | 不能承担的事 |
| --- | --- | --- |
| Control Console | 发起任务，展示计划、审核、进度、结果和生命周期控制 | 不直接写项目文件，不绕过 Control Server。 |
| Control Server | 分类、编排、审核、调用 Hermes/OMLX、调用 GameStudio Server、记录 artifacts、执行 evaluator | 不把模型输出当事实，不让模型自由决定动作名。 |
| Hermes | 模型网关和候选生成层，负责可观测地路由到 OMLX | 不直接写文件，不决定项目是否成功。 |
| OMLX | 本地模型推理资源，生成脚本候选、解释和少量高价值文本 | 不做项目编排、文件落盘、边界判断。 |
| GameStudio Server | 项目读写、脚本写入、编译、校验、图片生成、导出 | 不承担 reasoning session 和生产放行。 |
| `storage/projects` | 项目产物真相源 | 不由模型自由写入。 |

## 生产任务流

### S0 控制平面自检

目的：确认 Control、Hermes、OMLX、GameStudio Server 和 Editor 可启动、可访问、可被 Control 观测。

当前简要状态：已具备基本启动、自检、模型队列、heartbeat、runtime 状态和 GameStudio bootstrap flow。

未实现或待强化：一键取消当前生产测试、恢复 orphan session、运行态异常后的完整 UI 闭环。

### S1 文本互动故事闭环

目的：不依赖图片资产，先稳定完成可编辑、可校验、可导出的文本互动故事。

标准任务链：

```text
用户 brief
  -> Control 分类为 story workflow
  -> 创建项目
  -> 写入生成配置
  -> Hermes/OMLX 生成 scripts 候选
  -> 写入并读回 scripts.json
  -> 编译 blueprint.json
  -> 编译 project.json / story.json
  -> 结构与资源引用校验
  -> 导出 H5
  -> 基于 artifacts 返回结论
```

当前简要状态：主要能力已具备。Control 已有 story actions、GameStudio Server client、deterministic evaluator、失败短路和 artifact answer；文本故事闭环已能被验证。

未实现或待强化：真实生产时的模型脚本候选质量仍需稳定；fallback 候选必须显式标记，不能冒充模型创作成功。

### S2 图片资产闭环

目的：在 S1 文本闭环基础上，生成真实图片资产，落盘到项目并回填引用，然后重新校验和导出。

标准任务链：

```text
文本故事项目 artifacts
  -> GameStudio image/provider preflight
  -> Story Bible 或角色/地点/道具锁定
  -> 资产计划
  -> 串行生成背景/角色资产
  -> 图片文件落盘到 assets/
  -> 回填 project/story 资源引用
  -> 资源引用校验
  -> 重新导出 H5
```

当前简要状态：前置门禁已具备。Control 可执行图片 provider preflight、资产计划和背景候选的受控入口；未就绪时能阻断，不会把 prompt 或空 URI 当成图片成功。

未实现：完整图文资产闭环尚未完成。仍缺 Story Bible 到资产计划持久化、角色参考图、资产选择、引用回填、批量/连续分镜锁定、重新导出后的资源可用性验证。

### S3 生产运维闭环

目的：让长任务、模型异常、服务器重启、测试进程和人工审核都有可取消、可恢复、可追溯的边界。

当前简要状态：已具备模型任务队列、heartbeat、session artifacts、review records、部分 deterministic final answer 和 false-pass 拦截。

未实现：完整任务状态机、checkpoint 恢复、orphan session 收敛、proposal 晋级与回滚、批量生产队列和长期稳定性验证仍未完成。

## 放行标准

| 等级 | 必须通过 | 结论 |
| --- | --- | --- |
| S0 | Control/GameStudio/Hermes/OMLX 可启动和自检 | 控制平面可用。 |
| S1 | 模型链路、确定性事实、安全边界和文本故事闭环全部通过 | 可放行文本互动故事自动生产。 |
| S2 | S1 + ComfyUI preflight + 图片真实落盘 + 引用回填 + 重新导出 | 可放行完整图文故事自动生产。 |
| S3 | S2 + 运维、取消、恢复、日志追溯、false-pass 防护 | 可进入持续生产和批量任务。 |

## 动态模型切换评估与实施方案

目标：让 Control 在同一条生产任务内按阶段选择模型，把通用交互留给 `gpt-oss-20b-MXFP4-Q8`，把故事生成、场景校验、锁定事物等更严谨阶段切到 `Qwen3.6-35B`，同时保持可观测、可回放、可放行。

### 当前评估

当前实现状态补充：Control 后端已完成第一版阶段选模基础设施。`workflow.modelRouting` 已进入 Control 配置归一化，`story_scripts_candidate`、`story_blueprint_review` 已支持按 phase 选择模型并记录命中路由；GameStudio 的蓝图评审接口也已支持由 Control 显式传入 `provider/model/apiUrl` override。仍未完成的部分是 UI 配置入口、更多 GameStudio AI 阶段的 override 覆盖，以及多模型生产回归基线。

| 评估项 | 当前状态 | 结论 |
| --- | --- | --- |
| 整体切换模型 | 已支持保存左脑配置、预检并重启 Hermes 后切换单一运行模型；同时已补上部分 phase 级路由 | 已支持“部分同任务内按阶段切换”，但尚未覆盖所有 AI 阶段。 |
| Control 到 Hermes 的请求入口 | 已集中，模型请求统一经由 Control Server 发往 Hermes chat/completions | 具备集中加路由策略的改造条件。 |
| 阶段标签 | 已存在 `reasoning_decision`、`reasoning_plan`、`reasoning_answer`、`story_scripts_candidate`、`story_blueprint_review` 等 phase，且已用于路由 | 已可直接作为选模键。 |
| 路由配置 | Control 已支持 `workflow.modelRouting`，可对 phase/action 做模型映射 | 已能声明“故事生成用 A，蓝图评审用 B”，但 UI 尚未开放配置。 |
| Hermes 运行时绑定 | Hermes 运行时仍是单一 `HERMES_MODEL`；显式 phase 路由会由 Control 直接请求目标 provider/model | 已具备可用的多模型阶段路由，但 Hermes 自身仍不是完整多模型 runtime。 |
| 右脑/双路 runtime | UI 和控制接口里右脑仍未开放，不能直接作为生产可用的第二模型通道 | 不能把现有 right brain 视为已可用解法。 |

结论：当前 Control 已经从“只能整机切模型”推进到“部分阶段可动态切模”的状态。现阶段最先落地的是 `story_scripts_candidate` 和 `story_blueprint_review`，并同步打通了 GameStudio 蓝图评审 override；要达到完整生产要求，仍需继续覆盖更多 GameStudio AI 阶段、补 UI 配置入口，并建立严格阶段的可观测回归基线。

### 建议的生产路由策略

| 阶段 | 推荐模型 | 原因 |
| --- | --- | --- |
| 日常交互、请求分类、计划生成、最终答复、bootstrap、自检说明 | `gpt-oss-20b-MXFP4-Q8` | 成本更低、响应更快，适合高频交互和工具编排。 |
| `story_scripts_candidate` | `Qwen3.6-35B` | 故事结构、约束遵守、分镜文本稳定性要求更高。 |
| `story_blueprint_review` 与后续场景/蓝图严格校验 | `Qwen3.6-35B` | 需要更强的一致性检查、结构审阅和修复建议质量。 |
| Story Bible 到资产计划、锁定事物、连续分镜一致性分析 | `Qwen3.6-35B` | 这些阶段更依赖长上下文约束保持和细粒度实体一致性。 |
| 纯确定性 evaluator、项目读写、编译、导出、资源校验 | 不依赖模型 | 这些步骤必须继续由确定性事实和 GameStudio Server 结论放行。 |

原则：更强模型只能增强候选质量，不能替代 deterministic gate。即使引入 `Qwen3.6-35B`，最终放行仍必须由 artifacts、编译结果、校验结果和导出产物决定。

### 实施方案

#### 0. 配置归属：切换决策放在 Control，默认模型保留在 GameStudio 配置

结论：如果要支持“同一条生产任务内按阶段切换模型”，切换决策应放在 Control，而不是放在 GameStudio 的持久化配置侧。

原因如下：

- Control 负责 request decision、workflow_execute、review gate、artifacts、evaluator 和失败边界，天然拥有“当前阶段是什么、是否严格、是否允许降级”的上下文。
- GameStudio Server 的职责是项目事实读写、编译、校验、资产和导出；它可以有自己的 `scripts`、`prompt`、`image` 等默认模型配置，但不应该主导跨阶段生产策略。
- 如果把阶段切换写死在 GameStudio 配置里，Control 就无法基于同一条 reasoning session 的阶段状态、审核状态和 artifacts 统一决定“这一跳必须用哪个模型”，也不利于审计。

推荐边界：

- Control：拥有生产任务内的阶段路由表，决定当前 phase 或 action 该用哪个模型。
- GameStudio 配置：保留各能力域的默认 provider/model/apiUrl，例如 `scripts`、`prompt`、`image` 的默认值，供 Editor、独立调用或无上游 override 的场景使用。
- Control 调用 GameStudio AI 能力时：优先显式传入本次阶段的 `provider/model/apiUrl` override；未传 override 时，GameStudio 才回退到自己的 settings 默认值。

这意味着不应在生产任务执行中频繁改写 GameStudio 的 `studio_settings.json` 来完成阶段切换。`studio_settings.json` 更适合表达“本工作室默认怎么跑”，而不是“本次生产第 3 步临时切哪个模型”。

#### 1. 配置层：把单模型绑定升级为路由表

在 Control 持久化配置中新增类似 `workflow.modelRouting` 的结构，至少包含：

- `defaultRoute`：默认交互模型，初始指向 `gpt-oss-20b-MXFP4-Q8`。
- `phaseRoutes`：按 phase 选择模型，例如把 `story_scripts_candidate`、`story_blueprint_review` 指向 `Qwen3.6-35B`。
- `actionRoutes` 或 `stageProfiles`：给后续 `story_create_asset_plan`、锁定事物分析、连续分镜一致性检查等 action 级阶段预留精细化映射。
- `strictRouteRequiredPhases`：声明哪些阶段禁止静默降级，避免 `Qwen3.6-35B` 不可用时被悄悄切回 `gpt-oss-20b`。

默认策略应先做白名单，不做自动推断。也就是先明确指定少数高价值阶段走 `Qwen3.6-35B`，其它阶段继续走默认模型。

同时保留一条兼容规则：凡是 Control 未显式指定路由的 GameStudio AI 调用，继续走 GameStudio settings 中对应能力域的默认模型，避免破坏 Editor 和独立 API 使用方式。

#### 2. Control Server：新增统一选模器

在当前统一请求入口前增加一个 `resolveModelRouteForPhase(...)` 一类的选择器，输入至少包括：

- `phase`
- 当前 workflow action 或 step source
- 是否为 production test / deterministic fallback
- 当前 session 已记录的项目类型与 artifacts

输出应是完整路由对象：`provider`、`baseUrl`、`model`、`routeId`、`strict`。随后所有模型请求都走同一个选择器，不允许在业务代码里手写 if/else 散落切模。

#### 3. Runtime 层：从单模型运行时升级为多模型执行通道

这是本方案的关键门槛。当前运行方式更像“一个 Hermes runtime 绑定一个模型”。要实现真正的动态切换，必须二选一：

- 优先方案：Hermes chat/completions 支持按请求覆盖下游 `provider/baseUrl/model`，并把实际命中的模型写回日志与响应元数据。
- 保守方案：维护多条受控运行通道，例如 `gpt-interactive` 与 `qwen-strict` 两个命名 route，由 Control 按阶段选择不同通道，而不是靠重启 Hermes 临时改模型。

不建议把“切配置并重启 Hermes”当成阶段切换方案，因为它会破坏长任务连续性、锁冲突和可恢复边界，也不适合作为生产流水内的常规动作。

#### 4. 工作流落点：先覆盖高价值阶段

第一批只覆盖以下阶段，不要一开始全量铺开：

- `story_scripts_candidate`
- `story_blueprint_review`
- Story Bible 驱动的 `story_create_asset_plan`
- 锁定事物与连续分镜一致性分析阶段

请求分类、普通问答、状态说明、启动/自检类任务继续保留 `gpt-oss-20b-MXFP4-Q8`。这样可以先把更强模型预算集中到真正影响闭环质量的环节。

#### 5. 观测与失败边界

每次模型调用的 artifacts 必须额外记录：

- `routeId`
- `provider`
- `model`
- 是否命中严格路由
- 是否发生 fallback
- fallback 原因

若严格阶段指定 `Qwen3.6-35B` 但该路由不可用，默认应返回可观测失败或显式降级说明，不能继续产出一个看似正常、却没有标注降级的结果。

#### 6. 放行验证

在 S1/S2 放行前，新增一组模型专用回归要求：

- 同一任务中同时出现 `gpt-oss-20b-MXFP4-Q8` 与 `Qwen3.6-35B` 的路由证据。
- `story_scripts_candidate` 与 `story_blueprint_review` 的 artifacts 明确记录实际命中模型。
- `Qwen3.6-35B` 路由不可用时，系统能显式失败或显式标记降级，不能 silent fallback。
- 文本故事闭环成功率、蓝图评审稳定性、锁定事物一致性质量，相比单模型基线有可重复提升。

### 分阶段实施建议

| 阶段 | 目标 | 放行条件 |
| --- | --- | --- |
| M1 | 只完成配置结构、选模器和 artifacts 记账，不改变默认单模型行为 | 已完成后端基础设施。 |
| M2 | 打通 `story_scripts_candidate`、`story_blueprint_review` 到 `Qwen3.6-35B` | 已完成后端路由与蓝图评审 override，仍需生产回归确认稳定性。 |
| M3 | 扩展到 Story Bible、资产计划、锁定事物、一致性分析 | S2 相关流程能区分通用交互模型与严格阶段模型。 |
| M4 | 建立路由不可用时的降级/阻断策略与回归基线 | S3 运维闭环能取消、恢复、审计多模型任务。 |

## 当前未实现清单

- 完整图片资产闭环：真实图片落盘、角色/背景引用回填、资源校验、重新导出。
- 完整任务状态机：跨 session 的阶段流转、checkpoint、恢复和 orphan 收敛。
- 生产运维 UI：取消当前 reasoning session、停止当前 production test、恢复异常任务。
- 动态模型切换剩余项：补齐 UI 配置入口、扩展到更多 GameStudio AI 阶段、补严格阶段的降级/阻断策略，并完成生产回归基线。
- 安全自我强化闭环：`_inbox` proposal 的审核、测试、晋级、回滚和可视化审批。
- 批量生产能力：队列、暂停、取消、续跑、批量失败分类和重试策略。
- 模型/图片资源治理：OMLX pin/TTL/timeout、ComfyUI 串行队列和长期内存压力验证。
