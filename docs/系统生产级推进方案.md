## 1. 生产级目标

GameStudio 的生产级目标是：用户给出互动故事 brief 后，Control 能驱动 Hermes/OMLX 与 GameStudio Server，生成可验证、可编辑、可导出的 H5 互动故事项目。

系统判断标准不是"模型能回答"，而是完整任务链是否能留下可追溯证据：计划、审核、执行结果、项目文件、校验结果、导出产物和失败边界。

## 2. 系统分工（行为边界）

### 2.1 分层职责总表

| 组件 | 地址 | 职责 | 不能承担的事 | 由谁启动 |
|------|------|------|-------------|----------|
| **Control Console** | `http://127.0.0.1:8870` | UI 操作界面：chat、reasoning review、生命周期按钮、引擎配置 | 不直接写项目文件，不绕过 Control Server | `restart_control.sh` |
| **Control Server** | `http://127.0.0.1:2099` | 分类、编排、审核、调用 Hermes/OMLX、调用 GameStudio Server、记录 artifacts、执行 evaluator | 不把模型输出当事实，不让模型自由决定动作名 | `restart_control.sh` |
| **Hermes Gateway** | `http://127.0.0.1:8742/v1` | Agent 运行时：注入记忆、调用模型、返回结构化回答 | 不直接写文件，不决定项目是否成功 | Control Server 一键启动 |
| **OMLX** | `http://127.0.0.1:18888/v1` | 本地模型推理服务（OpenAI-compatible） | 不做项目编排、文件落盘、边界判断 | 独立进程，Control 负责检测状态并管理模型加载/卸载 |
| **GameStudio Server** | `http://127.0.0.1:1999` | 业务后端：项目 CRUD、编译、校验、资产生成、导出 | 不承担 reasoning session 和生产放行 | `start_project.sh` |
| **Storage** | `storage/projects/` | 项目产物真相源 | 不由模型自由写入 | — |

### 2.2 各组件明确行为

**Control Console 必须做的事：**
- 接收用户自然语言指令，发送至 Control Server
- 展示 reasoning plan、review 请求、step 进度和最终结论
- 提供生命周期按钮（启动、停止、配置保存、一键启动 Hermes）
- 在 1366x768 与 1920x1080 下保持可用
- 未配置 Provider 时给出明确阻断提示，不静默失败

**Control Console 禁止做的事：**
- 直接调用 GameStudio Server API（必须经过 Control Server）
- 直接读写 `storage/projects/` 文件
- 在界面上混用多套视觉风格或展示研发内部术语（P0/P1/P2/实验/临时）

**Control Server 必须做的事：**
- 收到请求后先做 request decision（确定性分类优先）
- 对命中固定 workflow 的请求，按注册 action 序列执行，不允许模型自由发明 action 名
- 对 write/edit/create/rename/delete/run 操作执行 review gate（`productionTest` 除外）
- 调用 Hermes/OMLX 时统一经由 model task queue，记录 `routeId`、`provider`、`model`
- 调用 GameStudio Server 时显式传入 `provider/model/apiUrl` override（如有）
- 基于 artifacts、evaluator 结果和项目文件给出最终结论
- 拒绝 workspace 外路径访问

**Control Server 禁止做的事：**
- 把模型输出当事实直接落盘
- 让模型自由决定 workflow 外的动作名
- 直接调用 ComfyUI（必须通过 GameStudio Server）
- 在活跃 reasoning session 中允许切换模型

**Hermes 必须做的事：**
- 按 Control 传入的 `provider/model/apiUrl` 路由模型请求
- 注入记忆文件（`ai/memory/` 下的 4 个权威文件）
- 返回结构化回答，记录运行时元数据

**Hermes 禁止做的事：**
- 自行决定写入文件
- 自行决定项目是否成功

**GameStudio Server 必须做的事：**
- 读写 `storage/projects/` 作为唯一真相源
- 生成 Story Bible 并持久化到 `project.state.aiBackground`
- 生成 asset plan 并持久化
- 执行编译、校验、导出
- 图片 provider preflight 失败后明确阻断，不把 prompt 或空 URI 当成图片成功

**GameStudio Server 禁止做的事：**
- 承担 reasoning session 管理和生产放行
- 跳过 Story Bible 阶段直接静默补齐缺失数据

**OMLX 必须做的事：**
- 提供 OpenAI-compatible API（`/v1/models`、`/v1/chat/completions`）
- 同一时间只加载一个模型（M2 32GB 内存限制）
- 健康检查响应 `/health`

**ComfyUI 必须做的事：**
- 在 `http://127.0.0.1:8188` 提供 `/system_stats` 健康检查端点
- 安装路径可通过 `COMFYUI_ROOT` 环境变量指定（默认 `/Volumes/ovokit2t/ComfyUI`）
- 通过 `start.sh` 脚本启动（`nohup sh ./start.sh &`）

**ComfyUI 生命周期约定：**
- Control 在自检（`gamestudio_ensure_running` / `gamestudio_self_check`）时，若 settings 中 `image.provider === 'comfyui'`，自动检测 ComfyUI 是否运行。
- 若 ComfyUI 未运行，Control 在 macOS 上通过 `osascript` 打开 **Terminal.app 窗口**并在其中执行 `sh ./start.sh` 启动。
  - **禁止**使用 `nohup` 后台隐藏启动；ComfyUI 的运行日志必须在可见终端窗口中输出。
  - 启动后轮询 `/system_stats` 直到就绪（默认超时 90s）。
- 若 ComfyUI 已运行但需重启，Control 先 `kill` 占用端口的进程，再打开新 Terminal 窗口重新启动。
- GameStudio Server **不直接启动 ComfyUI**；ComfyUI 的启动/重启由 Control Server 负责。

## 3. 模块结构与核心链路

```text
apps/control-console/   # Vue + Vite 控制台前端
apps/control-server/    # Node + Hono 控制服务后端
apps/server/            # GameStudio 项目读写、编译、校验、资产和导出服务
config/hermes/          # Hermes 左脑、路由、intent、skill 配置
state/                  # runtime events、reasoning sessions、review records
storage/projects/       # 项目产物真相源
```

核心执行链路：

```text
Control Console
  -> Control Server request decision
  -> workflow registry
  -> action schema / review gate
  -> Hermes / OMLX candidate generation when needed
  -> GameStudio Server API
  -> artifacts / evaluator
  -> final answer based on evidence
```

## 4. 启动流程

### 4.1 正确的启动顺序

```
Step 1: 启动 OMLX（独立服务）
  └─▶ oMLX.app / python3 -m omlx.cli serve --port 18888
  └─▶ 验证: curl http://127.0.0.1:18888/health
  └─▶ 若未启动：Control 自检时会检测到并提示

Step 2: 启动 GameStudio（业务平面）
  └─▶ ./start_project.sh --detached
  └─▶ 启动 server:1999 + editor:8868
  └─▶ 验证: curl http://127.0.0.1:1999/api/health

Step 3: 启动 Control 平面
  └─▶ ./restart_control.sh
  └─▶ 启动 control-server:2099 + control-console:8870
  └─▶ 验证: curl http://127.0.0.1:2099/api/health

Step 4: 一键启动 Hermes
  └─▶ Control Console UI: "⚡ 一键启动 (保存→自检→启动)"
  └─▶ 或调用 API: POST /api/control/agents/hermes-manager/runtime-action
  └─▶ 自检时会检测 OMLX 状态 → 加载模型 → 启动 Hermes
  └─▶ 验证: curl http://127.0.0.1:8742/v1/models
```

### 4.2 ComfyUI 自检与自动启动

在 Control 自检流程中，ComfyUI 的检测和启动按以下约定执行：

```text
Step: gamestudio_ensure_running / gamestudio_self_check
  └─▶ 读取 GameStudio settings → 检查 image.provider
  └─▶ 若 provider === 'comfyui'：
        ├─▶ GET {comfyuiBaseUrl}/system_stats（3s 超时）
        ├─▶ 若可达 → 通过，记录 comfyui=ok
        ├─▶ 若不可达 → 在 COMFYUI_ROOT 执行 ./start.sh
        │             → 轮询 /system_stats 直到就绪（默认 90s）
        └─▶ 若启动失败 → 标记 comfyui=fail，阻断后续图片资产步骤
```

启动命令（在 `COMFYUI_ROOT` 目录下，Terminal.app 窗口中执行）：
```bash
cd /Volumes/ovokit2t/ComfyUI && sh ./start.sh
```

Control Server 实际调用（macOS AppleScript）：
```applescript
tell application "Terminal"
    if not running then launch
    activate
    do script "cd '/Volumes/ovokit2t/ComfyUI' && sh ./start.sh"
end tell
```

重启命令（先 `kill` 端口占用进程，再打开新 Terminal 窗口）：
```bash
lsof -ti:8188 | xargs kill -TERM 2>/dev/null || true
# 等待 3s，若仍可达则 kill -KILL
# 然后由 Control 调用 AppleScript 打开新 Terminal 窗口执行 start.sh
```

### 4.3 重启脚本行为

| 脚本 | 行为 |
|------|------|
| `scripts/lifecycle/restart_control.sh` | 停止现有 control-server/control-console → 清理端口 → 重新启动 |
| `scripts/lifecycle/start_project.sh` | 启动 GameStudio Server + Editor；支持 `--detached` |

**已知问题**：`restart_control.sh` 偶发 port 占用需手动 kill（见 `PRODUCTION_DEFECTS.md` P1-06）。

## 5. 生产任务流

### 5.1 项目结构（真相源）

```text
storage/projects/<projectId>/
   meta.json       # 项目元信息和生成配置
   scripts.json    # 脚本层
   blueprint.json  # 蓝图层
   project.json    # 合成层项目数据
   story.json      # 运行时故事数据
   assets/         # 图片、角色、背景等真实资源
   builds/         # 导出产物
```

### 5.2 三层故事工作流

| 层 | 文件 | 职责 |
| --- | --- | --- |
| 脚本层 | `scripts.json` | 表达故事文本、顺序、选择点和结局意图 |
| 蓝图层 | `blueprint.json` | 把脚本卡片映射为可执行结构，锁定分支拓扑 |
| 合成层 | `project.json` / `story.json` | 承载运行态结构、真实资源、视觉表现和导出配置 |

脚本层可以由 AI 生成候选，但必须通过 schema/evaluator。蓝图层负责结构稳定，合成层负责真实资源和可运行表现。

### 5.3 S0 控制平面自检

目的：确认 Control、Hermes、OMLX、GameStudio Server 和 Editor 可启动、可访问、可被 Control 观测。

当前状态：已具备基本启动、自检、模型队列、heartbeat、runtime 状态和 GameStudio bootstrap flow；一键启动自愈（外来模型清扫 + 失败守卫收敛重试）与守护台四状态行已落地。

未实现：「停止 production test」等个别运维入口（其余取消/恢复/重试已在守护台 Sessions 与治理页落地，见 §13）。

### 5.4 S1 文本互动故事闭环

标准任务链：

```text
用户 brief
  -> Control 分类为 story workflow
  -> 创建项目 (step_story_create_project)
  -> 写入生成配置 (step_story_configure_project)
  -> Hermes/OMLX 生成 scripts 候选 (step_story_generate_scripts_candidate)
  -> 写入 scripts.json (step_story_write_scripts)
  -> 生成 Story Bible (step_story_create_bible)
  -> 编译 blueprint.json (step_story_compile_blueprint)
  -> Agent 评审蓝图 (step_story_review_blueprint_agent)
  -> 按评审修复蓝图 (step_story_repair_blueprint_if_needed)
  -> 图片前置检查 (step_story_preflight_image_provider)
  -> 编译合成层 (step_story_compile_compose)
  -> 校验项目 (step_story_validate_project)
  -> 导出 H5 (step_story_export_project)
  -> 基于 artifacts 返回结论
```

当前状态：P0 文本链路已达标。`productionTest=true` + `requireModelAnswer=true` 可完整执行 13 步无 review 阻塞。OMLX 生成真实故事内容（非 fallback）。Story Bible 可生成真实角色/地点（characters=4, locations=2）。

### 5.5 S2 图片资产闭环

标准任务链：

```text
文本故事项目 artifacts
  -> GameStudio image/provider preflight
  -> Story Bible / asset plan
  -> 串行生成背景/角色资产
  -> 图片文件落盘到 assets/
  -> 回填 project/story 资源引用
  -> 资源引用校验
  -> 重新导出 H5
```

当前状态：**已达标（2026-08-05 实测）**。前置门禁、锁定→线稿→渲染→审核→回填→导出闭环已在《狼来了》项目实测通过（3 角色锁定 + 线稿、11/11 场景图、dist 可玩），现行交付形态为「背景+立绘分层合成」全链路（22 步，见 `docs/狼来了内容质量闭环工作流.md`）。图片生成三级审核门禁（`pre_generate` → `lock_confirm` → `scene_bind`）与长任务进度（`/ai/tasks`）已具备。当前推进重点为内容质量闭环（完整度核实 → 定向修复 → 再核实）。

### 5.6 图片资产与锁定事物约定

目的：在文本故事闭环基础上，生成真实图片资产并锁定事物一致性，确保场景图中角色/道具/地点的连续性和稳定性。

**锁定事物标准流程（必须严格执行）：**

```text
Story Bible 已生成且有效
  -> 创建资产计划（asset plan）
  -> 识别需要锁定的资产（renderStrategy='ref_required'）
  -> 逐个资产执行锁定测试（lock test）
     -> 出图前审核（pre_generate，manual 模式；批准后才生成）
     -> 生成锁定测试图（ComfyUI workflow，单主体，512x512）
     -> AI 视觉评审（Kimi 视觉；passed=true 才能进入下一步）
     -> 人工确认锁定（lock_confirm，manual 模式；approve 才写 primaryReferenceAssetUri）
     -> 自动跟进线稿生成（ControlNet union，manual 模式下同样先走出图前审核）
  -> 所有必需资产锁定完成后，才可进入场景渲染
  -> 场景渲染时传入 referenceImages（IP-Adapter；主参考 0.9 + 线稿成品 0.5）
  -> 场景图落盘到 assets/ai/story_scenes/
  -> 人工确认绑定（scene_bind，manual 模式；approve 才回填 project.json/story.json）
  -> 校验项目（validate）
  -> 重新导出（re-export）
```

**硬性规则：**
- 没有 `primaryReferenceAssetUri` 的资产不得作为 referenceImage 传入场景渲染。
- 锁定测试图必须通过 AI 视觉评审（`passed=true`），且 manual 模式下必须经人工确认（`lock_confirm` approve）才落锁。
- 每张锁定测试图只能包含一个主要对象（单主体原则）。
- 场景渲染前必须检查所有 `referenceAssets` 是否已有 `primaryReferenceAssetUri`；缺少则阻断。
- 场景图必须经人工确认（`scene_bind` approve）才绑定到故事节点；批量渲染可用 approve-all 一次过审。
- 审核模式由 `STUDIO_IMAGE_REVIEW_MODE` 控制：`manual`（默认）/ `ai_only`（AI 评审即终审）/ `off`（全自动）；Control 驱动的调用默认旁路（control 已有步骤级审核）。
- 所有图片生成必须通过 GameStudio Server API，Control 不得直接调用 ComfyUI。
- 长任务（锁定测试、场景渲染、批量渲染）必须经 `/api/projects/:id/ai/tasks` 暴露进度，UI 轮询可见，禁止黑盒。
- 新 Story Bible 生成后，旧资产计划与提示词草稿全部作废（不跨故事继承）。

**当前状态：** 前置门禁、锁定→线稿→渲染→审核→回填→导出闭环已在《狼来了》项目实测通过（3 角色锁定 + 线稿、11/11 场景图、dist 可玩）。ComfyUI 能力检查与自动修复（`/api/ai/comfyui/capability-check`、`/auto-fix`）已具备。

### 5.7 S3 生产运维闭环

目的：让长任务、模型异常、服务器重启、测试进程和人工审核都有可取消、可恢复、可追溯的边界。

当前状态：已具备模型任务队列、heartbeat、session artifacts、review records、deterministic final answer 和 false-pass 拦截；orphan session 启动收敛（B03）、执行超时与取消（B04）、持久化任务队列与重试（C01/C02）、保留清理（C03）、gateway 监督恢复（C04）均已落地。剩余缺口（完整任务状态机语义、批量生产编排）见 §13。

## 6. 指令分类与路由规则

### 6.1 分类规则

指令通过启发式模式匹配（heuristics）进行分类，匹配 prompt 中包含的关键词/短语。分类优先级由 `config/hermes/routing/request_classification_rules.json` 中的 `priority` 字段决定（数值越高越优先）。

| 类型 | 说明 | 触发关键词/短语 | 优先级 | 需审核 |
| ---- | ---- | ---------------- | :----: | :----: |
| **answer_only** | 仅返回文本答案，不涉及项目事实。查询通用概念或原理。 | `是什么` `为什么` `解释` `说明` `区别` `含义` `原理` `建议` `是否合理` `会不会有问题` `对不对` `what` `why` `explain` `suggest` `reasonable` | 20 | 否 |
| **inspect_then_answer** | 查询系统状态、功能能力状态等信息。 | 项目状态查询、`项目能力状态查询` | 40 | 否 |
| **plan_then_answer** | 读取项目资料做检查，随后返回答案。默认兜底分类。 | 目录/文件/项目相关的查询词；对话继续词（`继续` `接着` `按照` `基于` `根据` `上面` `之前` `刚才` `这个设计` `这套方案` `实施` `推进` `修复` `落地` `同步文档` `计划` `规划` `方案` `检查` `分析`） | 55–95 | 否 |

### 6.2 工程原则

- 确定性分类优先；只有规则置信度不足时才调用 Hermes 做轻量分类。
- 命中固定 workflow 后，不允许模型自由发明 action 名。
- 模型输出只能作为候选，不是事实。

## 7. productionTest 模式

`productionTest` 是用于自动化测试的特殊模式，它会**完整 bypass 所有 review gate**：

- Plan review（运行任务图审核）
- Step review（步骤执行前审核）
- Write/edit/create/rename/delete/run 操作审核
- Quality gate（质量门人工确认）

### 使用方式

在调用 `POST /api/control/agents/:agentId/agent-runtime-sessions` 时传入：

```json
{
  "prompt": "生成一个小红帽的故事",
  "productionTest": true,
  "requireModelAnswer": true
}
```

| 参数组合 | 行为 |
|---------|------|
| `productionTest=true` + `requireModelAnswer=false` | 使用 deterministic fallback 脚本（不走 OMLX），最快完成 |
| `productionTest=true` + `requireModelAnswer=true` | 调用 OMLX 生成真实内容，完整 bypass review |
| `productionTest=false`（默认） | 正常 review 流程，mutation 步骤需要 approve |

**安全边界**：`productionTest=true` 仅用于自动化测试，禁止在生产环境默认开启。

## 8. 动态模型切换

### 8.1 当前评估

Control 后端已完成第一版阶段选模基础设施：`workflow.modelRouting` 已进入配置归一化；脚本生成实际由 GameStudio Server 负责，不再在 Control 侧按 `story_scripts_candidate` phase 路由。当前 Control 侧保留并支持按 phase 选择模型的阶段为 `story_blueprint_review`，GameStudio 蓝图评审接口也已支持由 Control 显式传入 `provider/model/apiUrl` override。

仍未完成：UI 配置入口、更多 GameStudio AI 阶段的 override 覆盖，以及多模型生产回归基线。

### 8.2 当前生产路由配置

当前生效配置（`config/hermes/manager.left-brain.json`，2026-08-19 核对；分工规则详见 `ai/BRAIN_DIVISION.md`）：

| 阶段 | 当前模型 | 说明 |
| --- | --- | --- |
| 日常交互、请求分类、计划生成、最终答复、bootstrap、自检说明 | `omlx / Qwen3.6-27B-MLX-4bit`（direct） | 左脑默认路由；成本更低、响应更快，适合高频交互和工具编排 |
| `story_blueprint_review` 蓝图评审 | `omlx / Qwen3.6-27B-MLX-4bit`（direct，strict） | `strictRouteRequiredPhases` 登记的 strict phase；路由不可满足时显式失败，不静默降级 |
| 故事脚本生成（GameStudio Server `generateScriptsCandidate`） | 由 GameStudio Server settings 配置（当前 OMLX） | Control 不侧路由该 phase；可经 override 显式指定 |
| 系统元分析 `meta_analysis` | `moonshot / kimi-for-coding`（direct） | 右脑专用：大上下文 + 强推理 |
| 右脑监察 `right_brain_supervision`（HERMES-H03） | `moonshot / kimi-for-coding`（direct） | 右脑专用：监察运行记录与受控建议，见 `ai/control_architecture.md` |
| 纯确定性 evaluator、项目读写、编译、导出、资源校验 | 不依赖模型 | 这些步骤必须由确定性事实和 GameStudio Server 结论放行 |

原则：更强模型只能增强候选质量，不能替代 deterministic gate。

### 8.3 配置归属

切换决策放在 **Control**，默认模型保留在 **GameStudio 配置**。

- Control：拥有生产任务内的阶段路由表，决定当前 phase 或 action 该用哪个模型。
- GameStudio 配置：保留各能力域的默认 provider/model/apiUrl，供 Editor、独立调用或无上游 override 的场景使用。
- Control 调用 GameStudio AI 能力时：优先显式传入本次阶段的 override；未传 override 时，GameStudio 回退到自己的 settings 默认值。

不应在生产任务执行中频繁改写 GameStudio 的 `studio_settings.json` 来完成阶段切换。

## 10. 错误处理与降级策略

### 10.1 各层错误处理

| 故障场景 | 当前行为 | 建议改进 |
|----------|----------|----------|
| OMLX 不可达 | 3 次重试后标记失败 | ✅ 保持 |
| Hermes Gateway 崩溃 | 无感知，下次状态检查才发现 | ❌ 需注册 `child.on('exit')` 自动重启（见 `PRODUCTION_DEFECTS.md` U-09） |
| 模型加载失败 | 返回 409，阻止启动 | ✅ 保持 |
| 模型切换失败 | 自动回滚旧配置+旧模型 | ✅ 保持，但 rollback 失败时可能留空模型（见 `PRODUCTION_DEFECTS.md` P0-03） |
| Config 未保存 | 返回 409 `config_not_saved` | ✅ 保持 |
| Preflight 失败 | 返回 409 `preflight_failed` | ✅ 保持 |
| 活跃 reasoning 中切换模型 | 返回 409 `reasoning_in_progress` | ✅ 保持 |

### 10.2 降级路径

```text
OMLX (18888) 不可用
  → 若配置了 OpenAI API Key → 降级到 OpenAI
  → 若配置了 Ollama → 降级到 Ollama
  → 无任何可用模型 → 返回 deterministic fallback

单模型约束：OMLX 同一时间只能加载一个模型（M2 32GB 内存限制）
  → 加载新模型前必须先卸载旧模型（loadProviderModel() 已实现）
  → 默认使用 Qwen3.6-27B-MLX-4bit
  → 出图期间由资源互斥调度（AUTO-R01）自动卸载/回载模型，状态见 `GET /api/control/resources/state` 与守护台「资源互斥」卡片
```

## 11. UI 约束

### 11.1 视觉约束
- 统一深色基底与单一强调色，不在同一页面混用多套风格。
- 组件状态只允许三种层级：默认 / hover / active，不增加额外花哨动画。
- 首屏与设置页优先信息清晰，不做装饰性大块渐变卡片。

### 11.2 布局约束
- 主界面固定三栏语义：列表 / 主操作区 / 说明。
- 设置页单页直出，不再使用"参数/检测"分标签切换。
- 避免嵌套滚动视觉；滚动能力保留但默认隐藏滚动条显示。

### 11.3 文案约束
- 只保留用户可执行信息，不展示阶段性研发术语（如 P0/P1/P2）。
- 说明文案必须与当前操作直接相关，避免历史背景与内部术语。
- Provider/Model 展示统一格式：`provider / model`，未启用显示 `无`。

### 11.4 交互约束
- 所有"测试连接"都在当前配置区就地执行，不跳转到二级页面。
- 弹窗顶部仅保留关键操作：`保存并应用`、`关闭`。
- 未配置 Provider 时，动作必须给出明确阻断提示，而不是静默失败。

### 11.5 发布前检查
- 检查是否出现多余滚动条、溢出遮挡、按钮不可见。
- 检查首页、设置页、AI 创建弹窗在 1366x768 与 1920x1080 下可用。
- 检查文案是否包含研发内部标记词（P0/P1/实验/临时）。
