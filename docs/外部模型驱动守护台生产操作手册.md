# 外部模型驱动守护台生产操作手册

> 面向对象：外部大模型操作员（如 GPT-6 等）——通过 HTTP 调用守护台（Control Plane），驱动 GameStudio 完成互动故事从创建到出图落地的完整生产。
> 本手册只记录**已实测验证**的链路与判据（截至 2026-10-08，经《小猫钓鱼》《乌鸦喝水》《假日出游》《公主穿衣》《小明的工作日》《小明的工作日2》六个故事生产验证）。
> 治理基准：遵守 `AGENTS.md` 正式工作流强制条款与 `PROJECT_GOVERNANCE.md`；本手册不改变任何既有审核门禁。

---

## 0. 为什么需要这份手册（外部模型当前的差距）

外部模型（如 GPT-6）直接照 API 列表调 GameStudio 会失败，原因不是缺接口，而是缺三样东西：

1. **生产链必须经过守护台事件分发**，直接散调 GameStudio 生成类 API 违反硬性治理（绕过审核门禁、无证据链），且会被客户端凭证拦截。
2. **链路中有多个"判断点"**（审图、驳回重渲、地点绑定修正、变体场景绑定）不是机械调用，本手册把每个判断点写成可执行清单，外部模型按清单执行并留证。
3. **多个异步/审核语义**（202 挂起、分发器超时、任务进度）不照文档读会误判成败，本手册给出每一步的判定规则。

## 1. 架构与角色边界

```
外部模型（操作员/监控者）
   │  HTTP + 客户端凭证
   ▼
守护台 Control Server  http://127.0.0.1:2099   ← 事件分发、审核门禁、资源互斥、租约
   │  事件分发（registry.v1.json 注册事件）
   ▼
GameStudio Server      http://127.0.0.1:1999   ← 项目/脚本/圣经/资产/出图/导出
   │
   ├─ oMLX 本地 LLM（Qwen3.6-27B-4bit，18888）——文本生成
   └─ ComfyUI（8188）——图像生成
```

**硬边界（违反即生产不成立）：**

- 生成类动作（出图/锁定/线稿/场景渲染/导出）**只允许经守护台 `POST /api/control/events/dispatch` 分发**，禁止外部模型直接调 GameStudio 的生成端点。
- 例外（允许直连 GameStudio 1999）：纯查询/CRUD/生命周期类——读 reviews、读 tasks、confirm-draft、读 story.json 核对。
- 任何一步失败**显式停止**（failed/blocked 留证），禁止带病继续。
- 工作区外路径一律拒绝。

## 2. 前置条件检查清单（开工前逐项确认）

| 检查 | 命令 | 通过标准 |
| --- | --- | --- |
| 守护台在线 | `curl -sS http://127.0.0.1:2099/api/health` | 返回 ok |
| GameStudio 在线 | `curl -sS http://127.0.0.1:1999/api/health` | 返回 ok |
| 资源互斥无悬挂 | `curl -sS http://127.0.0.1:2099/api/control/resources/state` | `gpuHolder/llmHolders` 为空或无异常长挂（悬挂处理见 §6） |
| 文本模型在线 | state 中 `modelOnline.loaded=true` 且为 `Qwen3.6-27B-4bit` | 不在线则等渲染批次结束后再加载（gpu/llm 互斥） |
| ComfyUI 能力 | `curl -sS http://127.0.0.1:1999/api/ai/comfyui/capability-check` | 节点/模型不缺 |

服务不在线时：本仓 `./start_project.sh --detached`；守护台 `sh /Volumes/ovokit2t/aiwork/local-agent-control/restart_control.sh`。

## 3. 接入方式（认证与判读规则）

### 3.1 分发调用

```
POST http://127.0.0.1:2099/api/control/events/dispatch
Headers:
  Content-Type: application/json
  x-client-id: <STUDIO_CONTROL_CLIENT_ID>          # 默认 gamestudio
  Authorization: Bearer <STUDIO_CONTROL_CLIENT_KEY>
Body:
{
  "event": "story.bible.generate",        // 事件 eventId（registry.v1.json）
  "payload": { "projectId": "...", ... }, // 事件 payloadSchema 定义的字段
  "caller": "workflow",
  "confirmed": true,                      // 仅持 review_approve scope 才生效，否则 409 审核流
  "targetProjectId": "gamestudio"         // 控制面项目标识，固定值；故事项目 id 放 payload.projectId
}
```

凭证从 GameStudio 仓 `.env` 的 `STUDIO_CONTROL_CLIENT_ID/KEY` 读取，**只使用不回显**。

### 3.2 四条判读铁律（ GPT-6 误判高发区）

1. **分发器 ~304 秒 fetch 超时 ≠ 失败**。圣经等长任务服务端继续执行；超时后必须查磁盘真相（project.json 的 `state.aiBackground.storyBible` 是否出现）再判。
2. **返回 `result.success=true` 且 HTTP 202/pendingReview = 挂起待审核**，不是完成。去查审核列表，批准（GS-32）后自动继续执行。
3. **`render_all_running` 409 = 有批次未收敛**。先查 `/ai/tasks` 与待审核，决断完毕再重试（F 系列已修收敛钩子，2026-10-08 之后版本）。
4. **任务进度真相源**：`GET http://127.0.0.1:1999/api/projects/:id/ai/tasks`（或 GS-35 分发）；审核真相源：`GET /api/projects/:id/ai/reviews?status=pending`。

### 3.3 审核操作（链内）

```json
// 批准：dispatch asset.review.approve { "projectId", "reviewId" }
// 驳回：dispatch asset.review.reject  { "projectId", "reviewId", "reason" }
// pre_generate 批准后自动重放原操作；scene_bind 批准即绑定，驳回后该场景重回缺口可重渲。
```

## 4. 标准生产链（逐步操作卡）

> 全程以《小明的工作日2》实测时序为参照：全链约 45 分钟（含继承加速；无继承的新故事需加抽卡/锁定/线稿环节，见 §5.4）。

### 步骤 1：创建故事（GS-39）

```json
{ "event": "story.project.create_ai", "payload": {
  "prompt": "<完整故事 brief：主角、设定、选择点、两个分支走向>",
  "title": "故事标题",
  "choicePoints": 1, "optionsPerChoice": 2, "endings": 2, "timeoutMs": 600000 } }
```

- 返回 `result.project.id` 为新项目 id。
- **验收**：读 `storage/projects/<pid>/scripts.json`，卡片数=2+选择点×(1+选项数)+结局数；选项文案互斥清晰；公式不符时停步重生成，不修补前进。

### 步骤 2：结构编译（GS-14 → GS-17）

```json
{ "event": "story.blueprint.compile", "payload": { "projectId": "<pid>" } }
{ "event": "story.compose.compile",   "payload": { "projectId": "<pid>" } }
```

- 均秒级返回。失败多为脚本结构问题，回到步骤 1。
- 毕业（直连，CRUD 类允许）：`POST http://127.0.0.1:1999/api/projects/<pid>/confirm-draft`，此后项目正式进入项目列表。

### 步骤 3：Story Bible（GS-13，长任务 5–10 分钟）

```json
{ "event": "story.bible.generate", "payload": {
  "projectId": "<pid>", "timeoutMs": 0,
  "input": { "title": "<标题>", "brief": "<brief>",
    "scenes": [ { "index": 1, "nodeId": "<story.json 节点 id>", "nodeName": "<场景名>", "summary": "<场景正文前 200 字>" } ] } } }
```

- scenes 数组从 `storage/projects/<pid>/story.json` 的 nodes 提取。
- **304s 超时正常**，查磁盘 `state.aiBackground.storyBible` 判定。
- **验收**：entities 覆盖剧情全部角色/关键道具/地点；每实体 `sceneRefs` 非空且语义正确（地点错绑是高频缺陷，见 §5.2）。

### 步骤 3.5：圣经质检（GS-50，2026-10-10 起必跑）

```json
{ "event": "story.bible.qc", "payload": { "projectId": "<pid>", "persist": true, "timeoutMs": 300000 } }
```

- 确定性规则检查（地点缺失/实体零出场/未知 id）+ 逐场景 LLM 对照复核 + 自动回写修正并作废旧计划。
- 返回逐场景差异报告（added/removed/reason）；**跑完必须抽读 2 个场景的修正理由**，确认质检没有误删。
- 质检后必须 GS-18 重建计划（sceneRefs 已变）。

### 步骤 4：资产计划 + 自动继承（GS-18）

```json
{ "event": "asset.plan.create", "payload": { "projectId": "<pid>", "rebuild": true } }
```

- **《xxxx2》命名约定**：标题以数字结尾且存在基底项目时，plan 落盘后自动继承基底已锁定资产（参考图/提示词四套/姿势变体/线稿/全局提示词+提示词闸）。响应含 `inherit` 汇总；地点锚点不继承（时间/氛围语境故事自有）。
- 匹配规则：名称规范化后精确匹配优先；近名 fuzzy（包含 ≥3 字/共享尾缀 ≥2 字，同类别唯一候选才采纳）。
- **验收**：`story-assets/plan.json` 每资产 `sceneIds` 非空（0 场景资产即缺陷，停步查圣经）；继承命中的 `referenceStatus=ready`。

### 步骤 5：导演构图（GS-49，本地 27B 约 5 分钟）

```json
{ "event": "story.composition.extract", "payload": { "projectId": "<pid>", "persist": true, "timeoutMs": 600000 } }
```

- 落盘 `plan.scenes[].composition`（元素位置/大小/层级/关系/原文依据）。
- **验收**：抽样 2 场读 composition，元素与剧情一致（地面站立角色 y≈0.85，浮空即缺陷）。

### 步骤 6：批量渲染背景（GS-34 + 审核门禁）

```json
{ "event": "asset.scene.renderAll", "payload": { "projectId": "<pid>", "backgroundOnly": true, "onlyMissing": true } }
```

- **必须 `backgroundOnly:true`**（全量模式喂透明抠图会洗白整图——F-57 事故）。
- 首次返回 202 + `pre_generate` 审核 → 批准后自动执行 → 每场景产出后再挂 `scene_bind` 审核。
- **逐张审图**（判断点，见 §5.1）：合格的批准（GS-32），不合格的驳回（GS-33 带原因）→ 修正根因后重跑本步（`onlyMissing` 只补缺口）。
- **验收**：`/ai/tasks` 中 `story.scenes.render_all` 收敛 done；7 场景背景全部绑定。

### 步骤 7：摆位（GS-41）

```json
{ "event": "asset.scene.placements", "payload": { "projectId": "<pid>", "applyComposition": true } }
```

- **验收**（读 story.json 的 `visuals.placements`）：角色全部上场；**冗余道具必须撤除**——角色已穿着的（西服/骑手服）、立绘已含的（骑姿变体含电动车）、背景已画的（衣柜里的挂装）不再摆道具抠图。
- 姿势变体上场确认：绑了 sceneIds 的变体应出现在对应场景摆位（poseHit 自动选用）。

### 步骤 8：导出（GS-08）

```json
{ "event": "project.export", "payload": { "projectId": "<pid>" } }
```

- 产物：`http://127.0.0.1:1999/demos/<pid>/latest/dist/index.html`。

### 步骤 9：走查验证（强制，禁止只导出不玩）

用 headless 浏览器（puppeteer-core + 本机 Chrome）从首页点到每种结局，逐屏截图：

- 每屏判读：背景语义 ✓、角色身份/服装 ✓、字幕不压关键主体 ✓、选项按钮可点 ✓。
- 双路径都走；ending 屏出现「重新开始」即通。
- 参考脚本：`.tmp/wd_walk.mjs`（换项目 id 与选项关键词即用）。

## 5. 判断点操作手册（外部模型必须执行的"人味"环节）

### 5.1 scene_bind 审图清单（每张场景图逐项过）

| 检查 | 通过 | 驳回动作 |
| --- | --- | --- |
| 地点正确 | 画面=剧情地点（婚礼在酒店不在卧室） | reject → 查场景-地点绑定（§5.2）后重渲 |
| 时间语境 | 白天/夜晚与剧情一致 | reject → 查地点锚点时间词（继承锚点不覆盖故事自有锚点）后重渲 |
| 空白/退化图 | 文件 >50KB 且内容可读 | reject（9–18KB 白图是已知退化模式） |
| 无人无动物 | 背景-only 画面无人物 | reject → 报缺陷（锚点污染） |
| 风格一致 | 与全局 worldAnchor 同风格 | reject 重渲 |

### 5.2 地点错绑修正（两故事三连撞的高频缺陷）

症状：重渲多次画面仍是错误地点。**显式 scenePrompt 压不住锚点引力**（promptLocks 仍拼接）。修法：

1. 读 `story-assets/plan.json` 的 `scenes[].assetIds` 与 **`promptAssets`**（内嵌地点对象），两者都要改——只改 assetIds 无效（实测）。
2. 把错绑地点换成正确地点资产（id/name/anchorPrompt/negativePrompt 同步换）。
3. 驳回旧图，重跑 GS-34。

### 5.3 姿势变体绑定（剧情阶段换装/换姿势）

继承或生成的变体（`plan.assets[].poseVariants`）默认 `sceneIds` 为空，不上场。按剧情语义绑定：

- 读每场景正文 → 判断角色在该场的服装与动作 → 选匹配变体写入 `sceneIds`（可绑多场景）。
- 同名变体优先级：`compStateHit > poseHit(sceneIds) > 表情差分 > 主参考`。
- 绑完重跑 GS-41（`applyComposition:true`），读 story.json 确认变体 projectAssetId 已出现在摆位。

### 5.4 无继承的新故事：多出三个环节

《xxxx2》以外的全新角色/道具需走完整锁定链（均有审核门禁）：

1. 提示词闸：AI 生成中文稿 → 确认 → 一键翻译 → 批准（向导第 4 步，事件链待补注册前可由人工在编辑器操作）。
2. 抽卡：每 ref_required 资产生成候选 → AI 评审 → 选定（参考图选定是语义判断点：白底/单主体/风格对/无穿戴关系）。
3. 线稿：锁定确认后自动跟进。

### 5.5 姿势库复用（换姿势的正确路径）

- 公共骨架库：`storage/_shared/pose_library/`（README 有补库与参数经验）。
- 绿幕 IPAdapter 直出换姿势**必然失败**（拉回主参考站姿），必须用骨架驱动链（`generateComfyuiPoseVariantSprite`）。
- 参数定案：身份参考用抠图、ipadapterStartAt=0.25、提示词以 `one single person only:` 开头、骨架尺寸=潜空间尺寸。
- 登记走正式链：`layered-produce` 的 `spriteAssetPath` + `sceneIds`。

## 6. 失败处置速查

| 症状 | 根因 | 处置 |
| --- | --- | --- |
| 分发 502/fetch failed @~304s | 分发器超时 | 查磁盘真相，服务端大概率已完成 |
| `render_all_running` 409 | 批次审核未收敛 | 决断全部待审 scene_bind（收敛钩子会自动关批次），再重试 |
| 资源 state 显示 gpu 长挂无任务 | 僵尸租约（F-65） | `POST /api/control/resources/lease/release {leaseId}`（本机操作员通道） |
| ComfyUI 节点报错但超时才发现 | 旧版轮询错误盲 | 升级本仓（F-64 已修：status_str=error 即时抛错） |
| 变体画面左侧半透明"幽灵人" | IPAdapter 漏参考图构图 | 身份参考换抠图 + ipadapterStartAt=0.25 |
| 结局场景总渲染成前一幕地点 | 圣经 sceneRefs 错绑 | §5.2 双字段修正 |
| 穿着西服的人旁边再摆一件西服 | 冗余摆位 | §4 步骤 7 验收规则，撤除道具摆位 |

## 7. 每轮留痕义务（治理硬性）

- 每步的 dispatch traceId、任务进度、审核决断（含驳回原因）自动留证；外部模型额外要记录：每次人工/模型判断的**理由**（写进 reject reason 或测试报告）。
- 故事完成后：更新 `docs/故事生产能力矩阵.md` 与新缺陷入 `docs/PRODUCTION_DEFECTS.md`。
- 阶段验收报告模板见《小型互动故事画面表达优化实施方案》§6–7（真值表、分维度评分、硬门禁）。
