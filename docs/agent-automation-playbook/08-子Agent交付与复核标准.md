# 子 Agent 交付与复核标准

## 1. 子 Agent 开始前必须回答

1. 我领取的 `task_id` 是什么？
2. 当前代码中控制行为的入口是什么？
3. 本任务不修改哪些范围？
4. 哪个测试最可能证明我的假设是错的？
5. 如果依赖未满足，我如何标记 BLOCKED？

没有这 5 项，不开始写代码。

## 2. 实施要求

- 先 inspect：读取任务指定文档、入口、相邻测试。
- 再 isolate：指出一个根因和一个最小改动点。
- 再 patch：只改任务范围内的文件。
- 再 verify：第一处实质编辑后立即运行最窄的验证。
- 再 close loop：逐项执行任务单的 acceptance；任一项未通过时，在同一 task 内定位、修复、重跑，直到全部通过或遇到真实外部阻断。
- 最后 report：只在 acceptance 全部通过、或存在无法由当前 task 解决的外部阻断时提交报告；不把“代码看起来正确”当测试。

### 任务内自检门禁

子 Agent 在提交报告前必须自行完成以下检查：

1. 把每条 acceptance 映射到至少一个明确测试或静态断言。
2. 检查同一模块是否仍保留与目标冲突的旧语义、旧常量、旧分支或旧汇总口径。
3. 对“统一/移除/全部/唯一”等需求，运行反向搜索证明旧实现不存在。
4. 测试失败、验收遗漏或残留旧语义时，继续修复当前 task；这不是等待项目经理确认的理由。
5. 只有依赖缺失、外部服务不可用、需求冲突或任务范围外的必要改动，才可以标记 `blocked`。

## 4. 项目经理统一复核顺序

本节只在 execution campaign 完成或被真实外部阻断后执行，不作为每个 task 自动推进的人工检查点。项目经理根据统一交付包复核全链路证据；若发现缺口，只退回对应 task，并要求重新执行受影响的后续验证。

### 第一关：范围

- 是否修改了任务范围外的行为？
- 是否破坏生命周期控制？
- 是否绕过 action registry、review gate 或 workspace 边界？

### 第二关：行为

- 正常路径是否成功？
- 失败路径是否阻断？
- 重试是否幂等？
- 取消、超时、重启是否收敛？

### 第三关：证据

- 测试是否真的执行了目标路径？
- artifacts 是否来自代码/接口/文件，而不是模型自述？
- 日志是否能用 task_id/session_id 关联？

### 第四关：回归

- 最小类型/语法检查。
- 任务相关测试。
- 受影响模块测试。
- 必要时执行生产测试阶段回归。

### 第五关：放行

只有满足以下条件才能标记 `passed`：

- acceptance 全部通过。
- 子 Agent 的 Acceptance 自检矩阵完整，且“统一/移除”类需求有反向搜索证据。
- 没有未解释的失败或 `other`。
- 没有新的 P0/P1 风险。
- 证据完整且可复现。
- 变更没有引入未审查的规则或权限扩大。

## 5. 统一验收不能通过时的处理

- 代码缺陷：退回同一 task_id 修复，不新建重复任务。
- 需求不清：`blocked`，列出需要确认的问题。
- 依赖未完成：`blocked`，列出依赖 task_id。
- 测试环境故障：记录环境证据，不能把环境故障判为代码通过。
- 风险超出范围：停止实施，升级项目经理。

## 6. 项目经理最终检查清单

- [ ] Phase A evaluator 不误放行
- [ ] 状态转移合法且可追溯
- [ ] checkpoint 可恢复
- [ ] orphan session 可收敛
- [ ] 任务队列可重启
- [ ] 超时、取消、重试有效
- [ ] 清理策略不伤害活跃任务
- [ ] Console 可操作关键运维动作
- [ ] API 暴露边界已限制
- [ ] P0 文本链路连续回归通过
- [ ] P1 图片链路通过后才宣称图片交付
- [ ] 多项目隔离和 proposal 治理有证据
