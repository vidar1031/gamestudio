# 自动生产系统总实施与测试计划

> 生效日期：2026-08-02。
>
> 本文是项目从当前状态走向最终目标的唯一工程实施规范。`ai/memory/DECISIONS.md` 定义架构决策；本文定义工程阶段、任务依赖、可测试验收与最终生产放行。发生冲突时，先遵守安全和架构决策，再以本文为执行顺序。

## 1. 最终目标

交付一个可长期运行、由人机协作治理的互动故事生产系统。

用户能够在守护台提出目标，也可以授权 Hermes 的 cron 按已批准的日程提交目标。Hermes 负责理解目标、触发已注册工作流和汇报状态；它不是生产数据的真相源，也不能绕过治理。Control 负责登记任务、执行受控工作流、保存状态、审核记录、证据与最终 verdict。GameStudio Server 负责真正创建项目、生成故事、校验并导出 H5。

最终系统必须满足以下可观察结果：

1. 用户可提交一次真实 P0 文本故事生产请求，并得到可玩 H5 或可解释的 `FAIL` / `BLOCKED`。
2. cron 可提交同类受控任务；它只能调用已注册工作流和治理 API。
3. 人可以在守护台查看任务、计划、步骤、审核、日志、产物与最终 verdict，并能在授权边界内批准、拒绝、取消、恢复或重试。
4. 任何模型、服务或质量失败都不能被显示为成功；真实产物、API 返回、测试和日志是结论证据。
5. 服务重启、模型短暂不可用、步骤超时、取消、重复触发不会让任务无限悬挂、重复破坏项目或丢失证据。
6. 多项目不会串写 artifacts、日志、配额或项目文件；新 workflow / proposal 不能自动变成生产规则。

## 2. 固定架构边界

### 2.1 Hermes 常驻助手层

Hermes 是 24/7 助手层，负责用户交互、已批准 cron、子 agent 监察、提醒和工作流触发。Hermes 必须通过 Control 的受控 API 提交生产意图；不得直接写 `storage/projects`、直接激活 proposal 或自行绕过审核。

### 2.2 守护台与 Control 治理层

守护台是人的治理入口。Control Server 是任务、状态、审核、证据、权限、队列和恢复的权威实现。所有写入、删除、导出和外部脚本动作都必须有 task/session 关联、审核记录和可复现证据。

### 2.3 GameStudio 能力层

GameStudio Server 执行确定性的项目创建、故事生成、蓝图、校验、导出与资产接口。它不决定任务何时开始，也不将模型文本当作事实。

## 3. 全局工程规则

1. 每个任务只修改已定义的范围；发现必要的跨范围改动时，先记录依赖和原因，再创建或补充任务单。
2. 每个任务必须执行“检查 -> 根因 -> 最小实现 -> 最窄验证 -> 漏项搜索 -> 修复 -> 完整验收矩阵”。
3. 每项“统一、删除、唯一、不得保留”要求都必须有反向搜索或等价静态断言。
4. 每项任务成功、失败、阻断、取消路径至少各有一个可测试例；不适用时必须说明原因。
5. Kimi 可在同一阶段内连续执行已满足依赖的任务，不得因为范围内缺陷等待人工确认。
6. Kimi 只能在外部服务不可用、需要真实凭证、需求冲突、安全风险、明确超范围的必要改动，或同一验收连续三次独立修复失败时停止并报告 `BLOCKED`。
7. 项目经理不做逐 task 许可；只在每一阶段的放行门和最终生产验收时独立审查。
8. 保护 `start`、`stop`、`pause`、`resume`、`exit`、`all-restart` 的现有语义。

## 4. 阶段 0：事实源与交互止血

### 目标

消除错误记忆、无效定时器、不可用人工审核和死路由，使后续自动化建立在真实状态上。

### 任务顺序

1. `HERMES-G01`：重建权威记忆并阻止垃圾落盘。
2. `HERMES-G02`：supervision 401 收敛。
3. `HERMES-G03`：聊天提交前确认可用性。
4. `HERMES-G04`：清理 `story_scripts_candidate` 死路由。

### 必测用例

- S0-01：写入“刷新本文件”等模板/指令文本，权威记忆拒绝落盘且记录原因。
- S0-02：写入有效状态或决策，后续读取路径能获得同一内容。
- S0-03：模拟 `meta_analysis` 401；监督器停止后续调度、记录认证阻断和恢复条件。
- S0-04：在可用测试凭证或 mock 环境中，监督器能按配置正常调度，不误判 401。
- S0-05：守护台人工全审模式发送请求后，提交确认、取消、拒绝均可见且有明确结果。
- S0-06：守护台自动直跑模式提交请求，不被人工弹窗路径阻断。
- S0-07：选择或调用旧死路由时得到明确不可用结论；真实脚本生成路径的 provider、transport、日志与文档一致。

### 放行条件

所有 S0 用例通过；权威记忆和 `TASK_QUEUE` 有效；不存在已知空转监督任务；人机审核界面可用。

## 5. 阶段 1：生产结论可信

### 目标

确保真实 P0 文本生产有可验证结论，失败不会伪装成成功。

### 任务顺序

1. `AUTO-A01`：evaluator false-pass 复核与修补。
2. `AUTO-A02`：统一 `PASS`、`FAIL`、`BLOCKED`、`CANCELLED`，移除 `SOFT PASS`。
3. 执行一次真实 P0 回归，并保留完整项目、日志、审核和导出证据。

### 必测用例

- S1-01：workflow step `ok=false`，最终 session/case/report 都为 `FAIL`。
- S1-02：evaluator `passed=false`，最终结果为 `FAIL`，包含 evaluator 证据。
- S1-03：evaluator 缺失或 `passed` 非 boolean，最终结果为 `FAIL`，不允许 PASS。
- S1-04：取消 session，所有载体为 `CANCELLED`。
- S1-05：等待人工审核，所有载体为 `BLOCKED`，并保留审核原因。
- S1-06：completed 且 final answer 缺失，最终为 `FAIL(final_answer_missing)`。
- S1-07：成功 session 有非空 final answer 和真实 artifacts，最终为 `PASS`。
- S1-08：对 verdict helper、生产测试脚本、人工菜单、统计运行反向搜索，不得存在 `SOFT PASS`、`soft-passed` 或第五种最终 verdict。
- S1-09：真实 P0 生产完成 create、script、Bible、blueprint、compose、validate、export；项目目录与导出物真实存在。

### 放行条件

所有 S1 用例通过；P0 真实运行产生一个可复查项目；任何失败路径均不被判为 PASS。

## 6. 阶段 2：可恢复执行引擎

### 目标

让生产任务脱离聊天窗口，成为可持久化、可取消、可超时、可重启恢复的实体。

### 任务顺序

1. `AUTO-B01`：状态机与合法转移。
2. `AUTO-B02`：step checkpoint。
3. `AUTO-B03`：orphan 扫描与 recover。
4. `AUTO-B04`：超时、取消与资源收敛。
5. `AUTO-C01`：持久化队列与 worker。

### 必测用例

- S2-01：每个合法状态转移成功并生成 task_id/session_id、from、to、reason、timestamp 事件。
- S2-02：非法状态跳转返回明确错误，既不静默修复也不覆盖旧状态。
- S2-03：成功 step 写 checkpoint，包含 nextStepIndex、输入/输出摘要和 artifacts 索引。
- S2-04：在 step N 后模拟 Control Server 重启，任务被识别为 orphaned，并从 N+1 恢复；已完成写操作不重复执行。
- S2-05：checkpoint 缺失、损坏或证据不完整时任务为 `BLOCKED`，不猜测继续。
- S2-06：模拟模型调用卡住，step/task 在显式 deadline 内结束为 timeout 或 failed，并释放 timer/heartbeat/锁。
- S2-07：取消 queued、running、terminal task；最终状态分别正确且重复取消幂等。
- S2-08：提交三个任务；同 projectId 串行，不同 project 受全局并发上限约束。
- S2-09：一个任务失败，独立后续任务仍被 worker 领取。
- S2-10：队列服务重启后未终结任务不会重复领取，能恢复或明确阻断。

### 放行条件

完成一次“提交任务 -> checkpoint -> 重启 -> orphaned -> recover -> terminal verdict”的端到端演练；队列和 worker 有持久化证据。

## 7. 阶段 3：长期守护与人机协作

### 目标

让人从逐步骤批准者变成异常处理者；让常驻助手可以安全触发任务，但无法绕过治理。

### 任务顺序

1. `AUTO-C02`：错误分类与有限重试。
2. `AUTO-C03`：缓存、session、日志保留清理。
3. `AUTO-C04`：gateway 监督恢复。
4. `AUTO-D01`：守护台任务运维入口。
5. `AUTO-D02`：Control API 访问边界。
6. `HERMES-H01`：守护台治理闭环。
7. `HERMES-H02`：cron 受控生产触发。
8. `HERMES-H03`：右脑子 agent 监察。

### 必测用例

- S3-01：网络/503 进入 `retry_wait` 并按配置退避；schema、权限、认证错误不盲重试。
- S3-02：达到最大重试次数后任务为 `FAILED`；取消后不会被重试。
- S3-03：TTL 清理只删除过期、终结、已归档记录；活跃任务、checkpoint、pending review、未归档 evidence 受保护。
- S3-04：gateway 异常退出被记录；有限重启成功时只恢复合法任务，超过上限时明确失败或阻断。
- S3-05：守护台能查看 queue/task 当前步骤、重试次数、审核、日志和 artifact；刷新后与服务端一致。
- S3-06：人在守护台取消、恢复、重试任务，得到成功/失败/阻断原因；生命周期控制不回归。
- S3-07：无凭证或非允许来源访问高风险 API 被拒绝；localhost 开发模式与合法凭证路径可用；日志不泄露 secret。
- S3-08：Hermes cron 只通过治理 API 创建已注册 workflow 的任务；不得直接写项目目录。
- S3-09：cron 发起真实 P0 任务，守护台能全程显示 task、步骤、审核、产物和最终 verdict。
- S3-10：右脑子 agent 只能读取健康/证据、提出建议或调用已注册的受控动作；越权 action 被拒绝且审计。

### 放行条件

一次 cron 触发的真实 P0 任务完整收敛；至少一次人为取消或审批动作可审计；至少一次模型或 gateway 故障正确重试或阻断。

## 8. 阶段 4：生产扩展与平台治理

### 目标

将可靠的 P0 生产平台扩展到图片资产、多项目和可治理的 workflow 生态。

### 任务顺序

1. `AUTO-E01`：角色资产生产。
2. `AUTO-E02`：锁定资产到场景渲染。
3. `AUTO-E03`：批量场景队列。
4. `AUTO-F01`：多项目隔离与配额。
5. `AUTO-F02`：proposal 测试、审核、晋级与回滚。
6. `HERMES-H04`：项目与 workflow 注册表。

### 必测用例

- S4-01：角色锁定图仅在真实文件存在且视觉评审通过后写入 `primaryReferenceAssetUri`。
- S4-02：缺失 reference 的场景渲染为 `BLOCKED`；合法 reference 被传给渲染输入，成功产物回填并通过 validate/export。
- S4-03：至少三个 scene 入队；单 scene 失败可按策略恢复，已成功 scene 不被覆盖。
- S4-04：两个项目并发或交替运行，projectId、artifacts、日志和配额无串写。
- S4-05：越过项目根目录的写入被拒绝；一个项目失败不污染另一个项目。
- S4-06：`_inbox` proposal 不可自动激活；经过测试和人工审核才可晋级；激活失败可回滚并保留版本记录。
- S4-07：注册第二个项目/工作流后，Hermes 只能看到其注册能力；两个项目使用同一治理模型但各自隔离。

### 放行条件

P1 图片链路、两项目隔离和 proposal 治理全部有可复现证据；第二个项目通过注册表运行至少一个受控 workflow。

## 9. 任务单完整性与新增任务规则

Kimi 不得因为任务单缺失而自行发明范围后继续实现。缺失任务单时，必须依照本文的任务目标、范围、必测用例、放行条件创建一个最小正式任务单，然后继续同一阶段。新任务单必须引用本节的阶段和测试编号。

`HERMES-H01`、`HERMES-H02`、`HERMES-H03` 和 `HERMES-H04` 已创建为正式任务单。Kimi 在开始对应阶段时必须读取它们，并按其前置依赖和本计划的测试编号执行。

## 10. 阶段交付包

每个阶段结束时，Kimi 提交一个阶段交付包，至少包含：

1. 本阶段完成与未完成 task 列表。
2. 每个测试编号的命令、结果、日志/产物索引；无法自动执行的真实服务测试要说明环境和手工复现步骤。
3. 修改文件、关键设计决定和兼容性说明。
4. 已知风险、阻断条件和下一阶段前置条件。
5. 一份反向搜索结果，证明已声明移除的旧语义不存在。

项目经理在阶段门进行独立复核；未通过时只退回失败 task，Kimi 修复后重跑受影响测试。

## 11. Kimi 持续执行流程

Kimi 启动 campaign 后按以下流程持续执行，阶段交付包是持久化检查点，不是等待人工许可的暂停点：

1. 读取本计划、当前阶段所有 task 文件、已完成任务证据和工作区未提交变更。
2. 选择当前阶段中依赖已满足的第一个 queued task，将其标记为 `in_progress`，记录开始时间和范围。
3. 在 task 内完成实现、最窄验证、失败修复、完整测试矩阵和反向搜索；将命令、结果和 artifact 索引写入 task 文件。
4. task 只有在所有 acceptance 和对应测试编号通过后才能标记 `completed`；范围内缺陷必须继续修复，不能作为遗留风险提交。
5. 当前阶段所有 task 完成后，运行本阶段全部 S 编号测试，写入阶段交付包和 `TASK_QUEUE` 状态，然后自动开始下一阶段。
6. 若上下文窗口、会话或工具进程中断，新的 Kimi 会话从 `TASK_QUEUE`、当前 task 文件、阶段交付包和 git diff 恢复；不得重新猜测进度或重复已验证的写操作。
7. 只有发生本计划定义的真实 `BLOCKED` 条件，或阶段 4 全部完成后，才停止自动推进并提交全项目统一报告。

## 12. 最终生产验收

所有阶段完成后，由项目经理执行最终验收，不接受 Kimi 自报完成。最终验收按以下顺序进行：

1. 环境检查：Control、守护台、GameStudio Server、Editor、OMLX、Hermes gateway 和图片服务按实际启用范围健康。
2. 安全检查：无 secret 输出；高风险 API 访问边界生效；生命周期控制仍可用。
3. 真实交互检查：用户在守护台提交 P0 任务并能看到治理记录。
4. 自动运行检查：cron 触发另一项已批准的 P0 任务；两项任务的 task_id、projectId、artifacts 与日志正确隔离。
5. 故障演练：分别模拟 evaluator 失败、模型暂不可用、Control 重启、step 超时和用户取消；每项均收敛到正确 verdict，无误放行、无限重试或证据缺失。
6. 产物检查：至少一个 P0 项目通过 validate/export 且可访问运行产物；若 P1 已启用，至少一个锁定角色资产和一个场景产物可追溯。
7. 治理检查：proposal 自动晋级被拒绝，人工审核后的合法 proposal 可激活或回滚。

只有上述检查全部通过，项目经理才能给出最终 `PASS`；任一关键失败为 `FAIL`，外部环境无法满足则为 `BLOCKED`。
