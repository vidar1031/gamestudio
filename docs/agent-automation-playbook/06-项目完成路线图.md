# 项目完成路线图

> 本文是当前项目管理主计划。子 Agent 不直接凭感觉选任务，必须从本文或 `07-子Agent执行任务清单.md` 领取任务。
>
> 当前判断日期：2026-08-01。

## 1. 项目最终目标

把 GameStudio 建成一个可以长期运行的互动故事生产系统：

```text
需求进入
  -> 任务登记
  -> 计划与依赖检查
  -> Control 编排
  -> Hermes/OMLX 生成候选
  -> GameStudio Server 写入真实产物
  -> evaluator / 测试 / 门禁
  -> 通过则交付，失败则重试、阻断或升级
  -> 任务证据归档与复盘
```

最终必须同时满足：

- 能完成：P0 文本故事从创建到导出可运行 H5。
- 能持续：多个任务连续运行，不因单个失败拖死全局。
- 能恢复：Control 或模型服务重启后，从 checkpoint 继续。
- 能证明：每个结论都有 artifacts、日志、测试和产物证据。
- 能治理：高风险写操作、规则变更和模型路由都有审核边界。

## 2. 当前真实状态

### 已具备

- Control Server、Hermes、OMLX、GameStudio Server 的基本分层。
- 受控 action registry 与 story workflow 计划生成。
- P0 文本生产链曾完成真实 E2E：创建、脚本、Story Bible、蓝图、合成、校验、导出。
- Reasoning session、heartbeat、cancel、orphan 标记和部分 recover 后端能力。
- 项目 evidence：项目目录、文件、build/dist 产物检查。
- S0/L1/L4 生产测试的基本分段思想。

### 当前卡点

1. `L4-04 evaluator false-pass`：评估失败时仍可能被判为 PASS，直接威胁放行可信度。
2. 完整任务状态机与阶段机未落地，session 状态不能完整表达 queued、paused、timeout、blocked 等生产状态。
3. 跨重启 checkpoint 恢复未形成闭环，已有 recover 后端但缺少稳定的持久化、扫描、UI 和回归验证。
4. 批量任务队列、暂停、取消、续跑尚未实现，当前更接近单 session 执行器。
5. Hermes gateway 曾被 control-server SIGTERM 终止，触发源和自动恢复仍需确认。
6. 会话与缓存长期累积：sessionCallCounts、inspectModelAccessCache、reasoning session 文件、chat history 都有清理问题。
7. P1 图片链路仍有 character asset pipeline、批量场景渲染、视觉评审兼容性和资源回填验证缺口。
8. Control Console 缺少完整的取消、恢复、队列、阻断和审核积压操作入口。
9. Control API 缺少认证，长期运行不能直接按当前状态暴露给非可信网络。
10. git 历史中的旧 Kimi key 已由人工轮换（2026-08-15 验证新 key 可用）。

## 3. 实施原则

- 先修放行正确性，再做并发和长跑。
- 先做最小可恢复队列，再做多项目并行。
- 先用现有 JSONL/文件存储验证模型，再考虑引入数据库。
- 所有新状态必须有明确转移规则，不允许用 `other` 吞掉未知状态。
- 所有模型输出都是候选，项目文件、接口返回和测试结果才是事实。
- 不得削弱 start/stop/pause/resume/exit/all-restart 生命周期控制。
- 主执行 Agent 一次只修改一个任务边界，任务内验收通过后可在同一 campaign 内自动推进依赖链；跨模块变更必须在交付中显式说明。

## 4. 阶段与依赖

### Phase A：放行可信度（前置阻断）

目标：修复“失败被判成功”的根问题，建立统一 verdict。

依赖：无。

完成条件：

- evaluator 失败必然产生 FAIL 或 BLOCKED。
- 所有 production test case 的 verdict 与 artifacts 一致。
- 增加至少一个故意制造 evaluator 失败的回归测试。

### Phase B：任务状态与 checkpoint

目标：让单个任务可暂停、取消、超时、重启恢复。

依赖：Phase A 的 verdict 语义。

完成条件：

- 状态集合和合法转移已固定。
- 每个 step 成功后持久化 `nextStepIndex`、输入摘要、输出 artifacts、错误分类。
- Control Server 重启后能扫描 orphan session 并提供可恢复结果。
- 恢复从 checkpoint 继续，不重复执行已确认成功的 step。

### Phase C：任务队列与长跑守护

目标：从单任务执行器升级为可持续任务调度器。

依赖：Phase B。

完成条件：

- 支持 queued、running、blocked、retry_wait、completed、failed、cancelled。
- 单项目默认串行，跨项目并发受限。
- 瞬时错误可退避重试，逻辑错误不盲重试。
- 单任务、单 step、全局队列都有硬超时。
- 长时间空闲、卡死、重复失败有告警和归档。

### Phase D：运维控制台与安全

目标：让人可以观察和接管长期任务。

依赖：Phase C 的 API contract。

完成条件：

- Console 能查看队列、当前 step、阻断原因、重试次数、证据和下一步。
- 能取消任务、恢复任务、重试失败 step、停止 production test。
- API 至少限制 localhost 或使用 `X-API-Key`。
- 不泄露模型 key、Provider key 和内部路径到普通 UI 文案。

### Phase E：P1 图片资产闭环

目标：在 P0 文本闭环可靠后实现可验证的锁定资产与场景图生产。

依赖：Phase A、B、C；且 P0 全量门禁通过。

完成条件：

- asset plan 持久化。
- ref_required 资产必须先锁定参考图。
- 锁定图必须通过视觉评审才可写入 primaryReferenceAssetUri。
- 缺失参考图时场景渲染必阻断。
- 场景图回填、validate、export 全部有证据。

### Phase F：多项目与自我强化

目标：支持多项目排队、失败样本复用和 proposal 安全晋级。

依赖：Phase C、D、E。

完成条件：

- 多项目隔离、优先级和配额明确。
- `_inbox` proposal 经测试、人工审核、晋级、回滚后才可生效。
- 规则变更自动触发回归测试。
- 不允许模型自行把 proposal 变成 active intent/workflow/evaluator。

## 5. 推荐实施顺序

1. P0-01 evaluator false-pass。
2. U-01 状态机与阶段机。
3. U-02 checkpoint 与 orphan recover。
4. P1-08/P1-11/P1-12 会话超时、重启和状态归类。
5. U-03 队列、暂停、取消、续跑。
6. P1-05/P2-04/P2-05 清理和 TTL。
7. U-06 运维 UI。
8. U-09 Hermes gateway 自动恢复。
9. P2-01 Control API 认证和本地暴露边界。
10. P1 图片资产闭环。
11. 多项目调度与 proposal 晋级。

## 6. 总体放行标准

项目不能以“某次 E2E 跑通”作为完成标准，必须满足：

- 连续至少 10 个代表性任务执行，P0 关键门禁零误放行。
- 至少模拟一次 Control 重启、一次 Hermes/OMLX 短暂不可用、一次 step 超时。
- 每次都能得到明确的 completed、failed、blocked 或 cancelled，不出现未解释的 `other`。
- 至少一次从 checkpoint 恢复并最终完成。
- 失败任务不会污染后续任务，也不会让队列永久卡住。
- 产物验证、测试结果、日志和最终 verdict 可以通过 task_id 关联。

## 7. 项目经理决策规则

- 主执行 Agent 在 campaign 内自行完成任务级实现、测试和修复，只在 campaign 完成或真实阻断时提交“实现 + 证据 + 未解决风险”的统一交付包。
- 本文中的卡点若被代码验证为已解决，必须同步更新状态和验收证据。
- 若一个任务发现跨越两个阶段，先拆分，不得扩大范围自行推进。
- 未通过前置阶段时，后续 Agent 只能做只读分析和测试准备，不得宣称交付。
