# 本地智能体项目执行实施方案

> 目标：让 Control + Hermes + GameStudio 的本地项目，可被本地智能体绑定后，以“可发现能力 + 受控执行 + 审核闭环 + 多轮优化”的方式自动推进创作，而不是依赖人工逐步点击按钮。
>
> 本文是对当前系统实施“项目能力驱动”的详细执行方案。它不是对现有代码的重写说明，而是项目的增量落地设计：在现有事件层、项目绑定、reasoning/session、review 门禁基础上，补齐“项目能力协议”和“执行状态机”，把聊天式本地智能体升级成真正的可执行项目操作代理。

---

## 1. 背景与问题定义

当前控制平面已经具备以下基础能力：

- 项目绑定：可绑定当前本地 GameStudio 项目
- 事件层：可读取事件注册表、发起事件分发
- reasoning/session：可创建执行会话、跟踪状态、审计证据
- review gate：可对 write / mutate / invoke / export 进行人工审核
- agent stream：可做咨询型聊天、只读分析与结构化输出

但这些能力仍然停留在“上下文识别层”和“控制层”，没有形成“项目执行层”。

当前的主要问题是：

1. 项目绑定只解决“知道绑定了哪个项目”，没有解决“这个项目到底能做什么”。
2. 事件映射只解决“事件发到哪里”，没有解决“动作该如何被安全执行”。
3. agent stream 语义偏咨询型，只允许只读工具，不具备真正的生产型动作契约。
4. 目前没有统一的“项目能力协议”，因此 agent 只能猜测、只能靠规则判断，不能稳定地发现并执行本地项目创作动作。

所以，当前问题不是“不能实现”，而是“能力边界还不完整，执行层缺失”。

---

## 2. 实施目标

### 2.1 总体目标

在不破坏现有 Control 运行时与 GameStudio 业务服务分工的前提下，补齐如下能力：

- 本地项目可被智能体绑定并发现
- 本地智能体可读取项目的能力、状态、事件、工作流和审计要求
- 智能体可在受控执行状态机中发起创作任务
- 智能体能进行多轮分析、校验、修正与再执行
- 全过程具备 review、artifact、trace、retry、rollback 的证据链

### 2.2 成功标准

以下条件满足后，说明项目已达到“本地智能体可执行创作”的基本能力：

- 智能体在绑定项目后，能列出项目的能力清单（read / write / generate / validate / export）
- 能发现项目的事件、workflow 和执行入口
- 能识别哪些动作需要 review，哪些动作可自动执行
- 能通过 plan -> execute -> validate -> review -> rerun 的闭环推进创作
- 能留存证据链：输入、决策、执行参数、输出、验证结果、审核记录
- 能在失败时 recover / retry / rollback，不造成无证据的静默失败

## 3. 设计原则

### 3.1 统一的项目能力约定优先

项目不再被当成“文件目录”，而要被当成“Agent Runtime”。

每个本地项目都必须提供一份能力声明，内容包括：

- 项目唯一标识
- 可执行能力列表
- 每个能力的 schema
- review 规则
- 资源与文件边界
- 事件入口
- 任务状态机

### 3.2 事件驱动仍然保留，但必须变成受控总线

事件层作为“动作总线”是合理的，但不能直接等同于“生产执行器”。

正确模型是：

- agent 生成计划
- runtime 把 plan 转成任务
- 任务进入事件总线
- 事件总线按 project capability 与 review gate 执行
- 成功/失败写入 evidence

### 3.3 agent 是计划与协调器，不是裸调用器

控制平面的智能体职责：

- 读取项目能力
- 分析任务目标
- 生成工作计划
- 选择对应 action
- 触发 review / validate / retry
- 记录全链路证据

但它不应该直接手工拼接底层 HTTP 请求来替代系统级执行器。

### 3.4 安全边界优先于自动化效率

本地创作过程必须遵守：

- 只读分析可自动执行
- 写入 / 生成 / 导出必须有明确门禁
- 涉及业务数据变更必须记录审计
- 项目外路径必须被拒绝
- 无证据的输出不能被判定为成功

---

## 4. 架构目标：三层结构

### 4.1 第一层：Project Capability Layer

项目能力层负责向外暴露项目“能做什么”。

核心对象：

- ProjectManifest
- ActionSpec
- CapabilityRegistry
- ProjectRuntimeDescriptor

作用：

- 让 agent 发现本地项目的可执行入口
- 让 agent 能判定一个动作是否在项目边界内
- 让 agent 知道调用前后需要什么 review / evidence

---

### 4.2 第二层：Execution Control Layer

执行控制层负责把 agent 的计划转成受控任务执行。

核心对象：

- TaskPlan
- ExecutionStateMachine
- TaskQueue
- ReviewGate
- RetryPolicy

作用：

- 把一段 agent 计划拆成有序 action
- 记录每个动作状态
- 进入 review / validate / retry / rollback
- 保护本地项目免受非受控调用

---

### 4.3 第三层：Evidence & Governance Layer

证据与治理层负责为所有输出保留可审计记录。

核心对象：

- ExecutionTrace
- EvidenceBundle
- ReviewRecord
- GovernanceAudit
- ArtifactIndex

作用：

- 记录 prompt、输入、动作、输出、验证结果
- 记录人工审核结论
- 为失败分析、回滚、修正提供事实依据
- 支持后续持续优化和评估

---

## 5. 项目能力协议设计

### 5.1 核心目标

一个本地项目必须能被智能体以标准协议发现，而不是靠文本说明和脚本猜测。

建议新增 `project capability manifest`，放在项目根目录中的稳定位置，例如：

```text
storage/projects/<projectId>/.studio/project-capabilities.json
storage/projects/<projectId>/.studio/project-runtime.json
```

或在控制平面中通过项目绑定服务动态生成能力视图（推荐前者更稳定，后者更易于动态扩展）。

---

### 5.2 能力声明结构

建议字段如下：

```json
{
  "version": "1.0",
  "projectId": "demo-story-001",
  "kind": "gamestudio-story-project",
  "displayName": "狼来了",
  "rootDir": "/Volumes/ovokit2t/aiwork/gamestudio/storage/projects/demo-story-001",
  "capabilities": [
    {
      "id": "story.generate",
      "type": "write",
      "label": "生成故事脚本",
      "requiresReview": true,
      "inputSchema": {
        "type": "object",
        "required": ["brief"],
        "properties": {
          "brief": { "type": "string" },
          "tone": { "type": "string" },
          "length": { "type": "number" }
        }
      },
      "outputSchema": {
        "type": "object",
        "properties": {
          "storyId": { "type": "string" },
          "scriptPath": { "type": "string" }
        }
      },
      "reviewPolicy": "manual_before_write",
      "artifacts": ["scripts.json", "story.json"]
    },
    {
      "id": "story.validate",
      "type": "read",
      "label": "校验故事项目",
      "requiresReview": false,
      "inputSchema": {
        "type": "object",
        "properties": {
          "projectId": { "type": "string" }
        }
      }
    },
    {
      "id": "scene.render",
      "type": "write",
      "label": "渲染场景图",
      "requiresReview": true,
      "inputSchema": {
        "type": "object",
        "required": ["sceneId", "referenceAssets"],
        "properties": {
          "sceneId": { "type": "string" },
          "referenceAssets": { "type": "array" }
        }
      }
    }
  ],
  "events": [
    "project.create",
    "story.generate",
    "story.validate",
    "scene.render"
  ],
  "workflows": [
    "story_production",
    "story_review",
    "story_export"
  ],
  "boundaries": {
    "allowedRoots": ["storage/projects/demo-story-001"],
    "disallowOutsideWorkspace": true
  }
}
```

### 5.3 能力发现流程

绑定项目后的默认行为应为：

1. 读取 project capability manifest
2. 读取事件注册表
3. 读取 workflow registry
4. 读取 project state snapshot
5. 汇总能力、风险、review 要求
6. 生成 agent 可消费的能力图

这样 agent 不再“盲试”，而是基于标准描述去做计划。

## 6. 本地智能体执行链设计

### 6.1 核心思路

执行链必须遵守这条顺序：

```text
bind project
  -> discover capabilities
  -> choose action
  -> validate schema
  -> check review gate
  -> dispatch controlled event / task
  -> execute with evidence
  -> validate output
  -> rerun or finalize
```

### 6.2 推荐的执行状态机

```text
idle
  -> planned
  -> ready
  -> executing
  -> waiting_review
  -> approved
  -> failed
  -> retry_wait
  -> completed
  -> rolled_back
```

规则：

- 只有 `ready` 状态才允许进入执行
- `waiting_review` 必须有人工或系统 review 结论
- `failed` 可进入 `retry_wait`，但必须遵守 retry policy
- `completed` 之后才允许收尾输出
- `rolled_back` 表示写入已撤销，输出不可视为成功

### 6.3 action 执行生命周期

每个动作都应该遵守：

1. 解析 action spec
2. 验证输入 schema
3. 校验是否满足 project capability
4. 检查 reviewRequired
5. 进入事件总线或 task queue
6. 返回 taskId
7. 轮询/监听执行状态
8. 收集 result artifact
9. 执行 validator
10. 决定 success / need revise / blocked

---

## 7. 事件驱动方案的改进版：受控事件总线

### 7.1 现状价值

当前事件层已经有：

- registry discovery
- event dispatch
- event runs history
- reviewRequired 检查

这说明事件总线是有效的基础设施。

### 7.2 需要补充的点

现在的事件分发仍不够“agent-native”，因为它没有完全绑定到 project capability。需要补齐：

- event -> action mapping
- event -> required capability mapping
- event -> result validator mapping
- event -> review policy mapping
- event -> retry/rollback mapping

### 7.3 推荐的任务执行路由

```text
agent plan
  -> resolve capability
  -> resolve event
  -> validate review policy
  -> enqueue task
  -> runtime 执行
  -> validator confirms outcome
  -> evidence stored
```

这意味着：

- 事件驱动保留
- 但事件不是直接拿来“猜”调用
- 事件必须通过 project capability + review gate + validator 才能执行

## 8. 智能体的实际职责分工

### 8.1 Planner

负责：

- 读取 project capability
- 选择合适的 action
- 生成 task plan
- 明确目标、输入参数、期望结果

### 8.2 Critic

负责：

- 对输出进行结果评估
- 检查是否满足目标
- 判断是否需要修正
- 决定是 retry / revise / prompt change

### 8.3 Executor Coordinator

负责：

- 把 plan 发到 task queue
- 监控 state
- 调用 review gate
- 在失败时触发 smart retry
- 收集 artifacts 并组织 evidence

### 8.4 Safety Gate

负责：

- 判定是否越界
- 判定是否在项目根目录内
- 判定是否触发未声明能力
- 判定是否缺 review
- 判定是否存在副作用风险

---

## 9. 统一的 review 与 governance 机制

### 9.1 操作分级

建议把项目动作分成 4 类：

1. Read-only
   - 可直接执行
   - 不影响项目状态

2. Draft generation
   - 允许创建候选草稿
   - 需保存版本，并可回退

3. Write mutation
   - 改写项目内容
   - 需要 review

4. External release / export
   - 导出、发布、跨项目调用
   - 必须有强 review 与 evidence

### 9.2 review 策略

建议支持以下策略：

- auto_allowed
- auto_with_versioning
- manual_before_write
- manual_before_export
- manual_before_external_invoke

并且每个 action 都带 `reviewPolicy`。这样 agent 不需要嘴硬地“猜”，而是直接从 spec 中拿到规则。

### 9.3 审计要求

所有写入类 action 需要记录：

- actor
- projectId
- taskId
- actionId
- input summary
- output summary
- review outcome
- time
- traceId

---

## 10. 多轮优化闭环

你要的不是一次性生成，而是“自动重试并优化”。

### 10.1 核心闭环

```text
task brief
  -> discover capabilities
  -> create draft
  -> validate output
  -> score result
  -> if fail -> revise prompt / parameters
  -> retry
  -> if pass -> lock result
  -> save evidence
```

### 10.2 实施约束

智能体必须在每轮都记录：

- 本轮目标
- 上一轮失败原因
- 本轮修正点
- 验证方法
- 是否发生 review
- 成功/失败结论

### 10.3 最终输出标准

最终答复必须基于证据，不是“模型说成功了就算成功”。

必须具备：

- 执行对象
- action result
- output file path
- validation status
- review status
- next suggested action

---

## 11. 数据与文件边界

必须遵守以下边界：

- 只允许访问绑定项目根目录下的允许范围
- 禁止访问 workspace 外路径
- 所有 write action 必须落在 project-root 之内
- 不能通过动态路径穿透到其它项目
- 所有大文件或资源产生的结果必须落在 `storage/projects/<projectId>/...`，不要写到任意目录

同时控制层必须增加：

- project root guard
- path traversal prevention
- file allowlist
- generated artifact index

## 12. 推荐的实现结构

### 12.1 需要新增的模块

建议新增以下关键模块：

- `apps/control-server/src/server/services/projectCapabilityService.js`

### 12.2 控制面 UI 需要新增的能力

- 项目能力面板
  - 当前项目能力列表
  - 可执行动作卡片
  - review 策略展示

  - 计划、执行、验证、重试状态

## 13. 实施阶段建议

### 阶段 1：能力协议与绑定增强

目标：让 project 具备标准化能力声明。

完成内容：

- 创建 ProjectManifest schema
- 扩展 project binding 结果，新增 `capabilities` 与 `runtimeDescriptor`
- 增强 `GET /api/control/project-binding` 返回能力摘要
- 增强 `events/registry` 读取与 capability mapping

验收标准：

- 绑定项目后，agent 能拿到能力总表，不再只是根目录信息

---

### 阶段 2：受控执行状态机

目标：将 agent 的“想法”变成受控任务。

完成内容：

- task queue
- action lifecycle
- retry policy
- execution state tracking
- evidence collection hooks

验收标准：

- 每个动作都可看到 taskId、state、review state、traceId

---

### 阶段 3：项目动作执行器

目标：让 capability 真正可执行。

完成内容：

- 编写 project action executor
- 将事件总线接到 action executor
- 回填 validator
- 自动判断是否可继续下一步

验收标准：

- 一个项目动作可以从 `planned -> ready -> executing -> validated` 流转完成

---

### 阶段 4：多轮优化闭环

目标：支持 agent 自动改进创作结果。

完成内容：

- 失败归因收集
- prompt / config revise
- new attempt
- score threshold
- best output retention

验收标准：

- agent 能在失败后自动修正并重试，且记录每轮策略变化

---

### 阶段 5：审计与治理完善

目标：保证生产过程可追溯。

完成内容：

- action 审计
- review with reason
- rollback
- output evidence pack
- governance dashboard

验收标准：

- 每次生成/导出/更改都能回溯到任务、原因、审核和结果

---

## 14. 实施风险与规避办法

### 14.1 风险：agent 直接调用底层接口

规避：

- 强制要求所有 action 通过 capability registry 与 executor
- 禁止绕过 action layer
- 对底层 HTTP 直接调用设置白名单限制

### 14.2 风险：项目边界被穿透

规避：

- 采用 rootDir + allowlist + path traversal guard
- 所有文件路径必须在 project root 内解析

### 14.3 风险：agent 输出被当事实

规避：

- 所有模型输出都视为 candidate
- 只有 validator / reviewer / deterministic check 才能确认成功

### 14.4 风险：多轮优化产生无止境循环

规避：

- 引入最大轮次上限
- 记录每轮修正原因
- 超过上限强制行文给出失败证据并终止

---

## 15. 交付物与验收标准

### 15.1 交付物

- project capability manifest 规范
- project runtime adapter
- execution state machine
- action executor
- review gate integration
- evidence collector
- project capability dashboard
- multi-round optimization runner

### 15.2 验收标准

交付完成的判定条件：

1. 绑定项目后，agent 可以列出其 capability
2. agent 能在 project root 内安全执行有权限的动作
3. action 执行过程可见 task state / review state / evidence
4. 失败时可 retry / recover / rollback
5. 输出必须基于 evidence，而不是模型口头断言
6. 项目可在 controlled workflow 中自动生成、校验和导出

## 16. 结论

当前系统已经具备：

- 项目绑定
- 事件分发和可观测执行
- review gate
- reasoning session
- runtime control

但还没有形成“本地项目的 Agent Native Runtime”。

要实现“本地智能体操作任意 GameStudio 项目进行创作生产”，必须新增：

- 项目能力协议
- 统一 action 表达
- 受控执行状态机
- 证据链与 audit
- review / retry / rollback
- multi-round optimization loop

这才是从“聊天式分析器”升级为“本地项目自动创作执行器”的关键路径。

它不是单一 API 调用，而是完整的 project runtime contract。只有完成这个层次的补齐，agent 才能真正做到：绑定项目 -> 发现能力 -> 规划任务 -> 执行生产 -> 校验结果 -> 迭代优化 -> 交付成果。

---

## 17. 对当前系统的落地建议

建议优先执行以下序列：

1. 项目能力 manifest 规范
2. project binding 返回 capability summary
3. action executor 与 state machine
4. review gate 对接到 action 执行器
5. evidence collector 接入 reasonings / tasks
6. 多轮优化 runner
7. 控制台能力面板

若先做 UI 视觉或事件路由增强，而不先做 project capability contract，最终仍然会回到“客户端猜动作、服务器拦截、空回答”的状态。

这也是当前错误的根源：没有能力层，就没有真正的自动创作执行层。
